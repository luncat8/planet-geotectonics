# 0.3 — GPU smoothness and measurement plan

Continues `0.2-plan.md` after Phase H. The CPU engine and the GPU kernel graph
are done and parity-gated. What is left: the GPU engine must *feel* as good as
the CPU one, and every claim in this plan must be backed by a measured number,
not by an average.

Symptoms on hardware (the reason this plan exists):

- GPU play shows periodic lags and is not as smooth as CPU play.
- The perf strip (500 ms EMA) shows nothing wrong while the picture stutters —
  an average cannot see a 30 ms spike among 4 ms frames.
- Throughput scales oddly with the steps/frame setting (1 step per frame is
  much worse per step than 5), which points at per-frame fixed cost and
  per-frame CPU sync, not at the GPU kernels themselves.

Known suspects, in expected order of impact:

1. The event round trip on the frame path: every `eventCadence` (1 Myr, i.e.
   every 10 steps at dt 0.1) `GpuSim.step` awaits a full download (~7.5 MB at
   L5: 11 staging copies + `mapAsync` + unpack), runs `Events.cycle` on the CPU
   mirror, then re-uploads everything. GPU queue idle, rAF blocked, cost varies
   with tectonic activity (splits/merges) → irregular hitches.
2. Per-step overhead: one encoder + submit + ~50 dispatch encodes +
   `uploadFrame` write per step, so N steps/frame is N times the fixed cost.
3. One superlinear GPU kernel: `loserRank` loops every loser over all
   `aliveN()` columns (O(losers × colCap), global memory). Quiet frames fine,
   heavy-overlap epochs (big collisions/sutures) spike.
4. Checkpoint every 20 Myr: another full download + whole-state serialization
   on the frame path.

Atomics (per-cell cursors, ≤~40-contender plate counters) and branching
(ring ≤6, donors ≤3, loser chains 6 fixed dispatches) were reviewed and are
not the cause; this plan does not touch them.

Order: **instrument and capture a baseline → remove suspect 1 → suspect 2 →
suspect 3 → polish and extend to L6.**

## 0. Conventions

Per `0.2-plan.md` §0 and `AGENTS.md`, plus:

- Distribution stats are first-class: the perf strip keeps its EMA for
  averages, but gains p95/max frame gap over a 1 s window (preallocated ring,
  rebuilt at the same 2 Hz, no allocation in the frame loop) and event
  round-trip timings (download ms, events ms, upload ms, checkpoint ms).
- Every phase ends with the regression gate: `node tests/run-all.js`, the GPU
  parity ensemble (`node tests/gpu-parity.js 1000 --ensemble` over the
  headless rig), and a bench run compared against the previous phase's
  committed baseline. A phase that moves world evolution (event timing) must
  keep the release profile bit-identical or re-prove the long-run statistics;
  the parity ensemble is the arbiter.
- Baselines are committed runs in `experiments/logs/` (existing convention:
  keep useful logs), named `0.3-<phase>-<description>.txt`.

## Phase I — Instrumentation and baseline (1 d)

Goal: make the three suspects visible as numbers, then record the "before".

- **I1. GPU query sets in `GpuSim.frame`.** A timestamp query set resolves
  dispatch-group boundaries (one pair per kernel name, like the CPU
  `Perf.lap` ids) into a preallocated buffer; results are read back one frame
  late via `mapAsync` and folded into the 2 Hz strip as per-kernel GPU ms.
  Query sets are not universal (SwiftShader may lack `timestamp-query`):
  feature-detect and fall back to wall-clock ms/step with a note in the strip.
- **I2. Perf strip distribution stats.** Frame gap ring + p95/max, event
  round-trip wall times around `download`/`Events.cycle`/`uploadState`,
  checkpoint push time. The strip then shows e.g.
  `p95 21.4 ms · max 63 ms · events 12 (7.1 ms)` next to the existing EMA line.
- **I3. Bench, two modes, both time-boxed (~1–2 s each):**
  - `experiments/gpu-bench.js` over the existing headless rig (same
    `PGT_CHROME` plumbing as `tests/gpu-parity.js`): (a) step isolation —
    submit one frame, await `queue.onSubmittedWorkDone`, repeat; report GPU
    ms/step at L5 (and L6) for 1/5/20 steps; (b) smoothness — play at a fixed
    config, record per-rAF step count and frame gap; report median/p95/max gap
    and hitch count (gaps > 2× median).
  - An in-page bench mode (a "Bench" button or `?bench=1` on `index.html`)
    running the same two modes so the owner's own GPU gives the real numbers.
- **Baseline commit:** I3 output at the current build, L5, dt 0.1, 1/5/20
  steps, map start and a hot start; expected to show the event spikes in p95/max
  and the per-step fixed cost in the 1-vs-5 step gap.

Acceptance: per-kernel GPU ms table visible at 2 Hz; baseline logs committed;
regression gate green; no measurable change to the frame path (I1/I2 must cost
< 0.1 ms/frame at L5).

## Phase II — Events off the frame path (1–2 d)

Goal: the rAF loop never waits on a download, events, or an upload.

- `GpuSim.step` keeps its current awaited contract (tests, parity harness,
  single-Step button). The play loop gets a new path, `GpuSim.play(state, dt,
  n)`:
  - submits n frames to the queue (Phase III makes that one encoder; until
    then n submits, as today);
  - on an event or checkpoint due date it does not await: it kicks a background
    task — staging copies submitted, `mapAsync` in flight — and stores the
    promise;
  - when the task resolves, `Events.cycle` (span-aware, as already coded with
    `span = t − lastEvent`) runs and `uploadState` is queued; the next
    `play` call submits the upload before its frame, so events take effect from
    the following frame.
  - Events were already one cycle late by design ("the CPU mirror is only
    pulled in for plate events (one cycle late)"); this adds at most one more
    cycle of latency, and only when the GPU falls behind.
  - In-flight task already present at the next due date (fast forward on a slow
    GPU): queue depth 1; on overflow fall back to the old synchronous round
    trip so the cadence is never skipped. Skipped event cycles are forbidden —
    the CPU reference runs one every `eventCadence`, and the release profile
    must stay comparable.
- Checkpoints ride the same background task (serialize after the upload, push
  to the ring when done).
- The UI `gpu.busy` guard stays for user-initiated Step/Save/Probe; play frames
  no longer serialize on it.

Acceptance (measured, vs the Phase I baseline, same config):

- p95 frame gap ≤ 2× median while playing at dt 0.1, 5 steps/frame, for a
  ≥ 200 Myr hot-start run that includes split and suture activity (the
  4500 Myr run-to-target is the soak).
- Event round-trip ms still visible in the strip (it is still happening), but
  no longer present in the frame-gap distribution.
- Throughput at 1/5/20 steps ≥ baseline.
- Parity ensemble green; release profile statistics unchanged.

## Phase III — N steps in one command buffer (1 d)

Goal: per-step fixed cost (encoder + submit + `uploadFrame` write + JS) paid
once per rAF, not once per step.

- `GpuSim.play` precomputes n `frameIn` blocks on the CPU before encoding: the
  mantle bookkeeping (`Tm`, precession, plume spawns, wave phase) is
  sequential and cheap, and keeping it on the CPU is the design's split
  ("the CPU state stays the owner of everything sequential"). `frameIn`
  becomes n×74 floats per call (buffer grows with the max n, 20); one encoder
  carries n× the dispatch list of `frame()`, one submit.
- Same dispatch order and same input values as n separate `frame()` calls, so
  results must stay bit-identical on the same device: the parity harness and
  the frame-2 clone test are the checks (the clone test specifically catches
  "same numbers, wrong decision path" drift).

Acceptance:

- GPU ms/step from the I3 step-isolation bench: 1 step ≈ 5 steps ≈ 20 steps
  within 10% (the 2.5× gap seen today must be gone).
- Parity harness: same-device bit-identical; ensemble green.

## Phase IV — `loserRank` without the O(losers × n) scan (0.5–1 d)

Goal: turn the only superlinear kernel into a bounded one.

- Losers are already binned per winner (`loserCount` + `scanC` offsets).
  Rewrite as one workgroup per winner: load the winner's L_w bin entries into
  workgroup memory, compute each entry's rank by index (L_w²/2 local
  comparisons, trivially parallel in the workgroup), write `loseList`.
  Worst case is one giant winner (L_w ~ colCap during a mega-collision):
  chunked workgroup memory handles it; typical L_w is single digits.
- The rank definition (index order among a winner's losers) is unchanged, so
  the output list is identical — this is a bit-identical refactor, and the
  parity harness proves it.

Acceptance:

- Contact-block GPU ms (I1 query sets) reduced ≥ 5× in a heavy-overlap rig —
  a new `experiments/` config that maximizes per-frame overlaps (e.g.
  `plateCount 4`, low `vSuture`, hot start) with the overlap count logged from
  the frame counters to show the load was real.
- Parity: same-device bit-identical; ensemble green.

## Phase V — Polish and L6 (1–2 d)

- Merge the render pass into the play encoder: one submit per rAF for
  sim + draw instead of two (acquire the canvas texture, append the render
  pass after the compute passes in `play`).
- UI: level select (L5 / L6, L6 offered on the GPU engine per the
  "CPU JS first (L5), then WebGPU (L6–L7)" policy) and an event-cadence
  select (1 / 5 / 10 Myr) as the user-facing fast-forward escape hatch;
  default stays 1 Myr so the canonical run is unchanged.
- Bench matrix extended to L6 (I3 both modes); L6 baseline committed.

Acceptance: L6 playable at 1–5 steps/frame with p95 ≤ 2× median on the
calibration host's hardware; SwiftShader numbers recorded as relative only
(existing convention). All earlier gates still green.

## Risks and how the plan handles them

- **Query-set portability** (missing on some SwiftShader builds): feature
  detect, wall-clock fallback, and the headless rig already documents which
  flags the container needs.
- **Event staleness changing long-run statistics:** the cadence is never
  skipped (overflow falls back to the synchronous path), `Events.cycle` is
  span-aware, and the gates are the parity ensemble plus the release profile;
  any statistics drift is a plan failure, not a tunable.
- **N-step encoder breaking parity:** bit-identity is an acceptance criterion,
  checked by the frame-2 clone test and the 1000-frame ensemble before the
  phase is closed.
- **Bench on the wrong device:** every reported number carries its device
  string (adapter info at boot); SwiftShader is labeled as relative-only,
  matching the existing BENCH convention in the sibling project.
