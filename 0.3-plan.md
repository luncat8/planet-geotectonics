# 0.3 — GPU smoothness and measurement plan

Continues `0.2-plan.md` after Phase H. The CPU engine and the GPU kernel graph
are done and parity-gated. What is left: the GPU engine must *feel* as good as
the CPU one, and every claim in this plan must be backed by a measured number,
not by an average.

Symptoms on hardware (the reason this plan exists), from the owner's rig
(`experiments/logs/0.3-2.txt`, nvidia/ampere, Chrome 151, L5, dt 0.1):

- GPU play shows periodic lags and is not as smooth as CPU play: playing 1
  step/frame the strip reads `108.4 fps · frame 34.4 ms · p95 66.6 ms · max
  77.9 ms · events 4 (114.7 ms)` while the CPU engine at the same settings reads
  `90.3 fps · frame 11.3 ms · p95 11.2 ms · max 16.7 ms` with no event line at
  all.
- The event round trip dominates: 4 cycles inside one 500 ms strip window, each
  ~114.7 ms, against a ~9 ms frame interval. At 1 step/frame an event is due
  every ~93 ms, so the round trip costs more than the time between round trips.
- The perf strip's two averages disagree (`108.4 fps` is 9.2 ms, `frame 34.4
  ms`) because one is E[1/gap] and the other E[gap] over a skewed distribution —
  which is exactly why the strip also carries p95/max.
- Throughput scales weakly with the steps/frame setting: the step-isolation bench
  gives 8.900 ms/step at 1 step and 7.220 ms/step at 5, a 1.23× gap, so the
  per-step fixed cost is ~1.7 ms of a ~7 ms step.

Suspects, in the order the measurements settled them:

1. **The event round trip — confirmed and root-caused (Phase II).** It was not
   the download or `Events.cycle`: measured headless, the cycle is ~2 ms and the
   pack/unpack was ~200 ms at L5, of which the dominant part was a per-element
   `ArrayBuffer` allocation in the f32-bits reinterpret of the edges block, plus
   shipping arrays the frame kernels recompute anyway, plus walking dead column
   rows. See `experiments/logs/0.3-II-roundtrip-cost.txt`.
2. **Per-step fixed cost — real but small (Phase III).** ~1.7 ms/step at L5 on
   this rig, so one encoder per rAF is worth ~20% at 1 step/frame, not the 2.5×
   an earlier rig suggested.
3. **`loserRank`'s O(losers × n) scan — measured small at L5 (Phase IV).** The
   timestamp table on the owner's rig puts it third at 0.29 ms behind `winners`
   0.56 and `diagC` 0.41, i.e. ~4% of a 7 ms step in a quiet frame; it still
   matters in heavy-overlap epochs.
4. **Checkpoint every 20 Myr — same transfer as the event round trip**, so it
   shrinks with it (Phase II); it keeps the full mirror because
   `Checkpoint.save` serializes it.
5. **The K11 diagnostic passes, every frame — new, and the largest remaining
   single item.** On a saturated queue `diagA` + `diagC` are 2.67 ms of the
   6.74 ms top-10 kernel total at L5, and no device code reads their output
   (Phase III).

Atomics (per-cell cursors, ≤~40-contender plate counters) and branching
(ring ≤6, donors ≤3, loser chains 6 fixed dispatches) were reviewed and are
not the cause; this plan does not touch them.

Order: **instrument and capture a baseline → make the round trip cheap →
diagnostics off the frame path → N steps in one encoder → `loserRank` → polish
and extend to L6.**

## 0. Conventions

Per `0.2-plan.md` §0 and `AGENTS.md`, plus:

- Distribution stats are first-class: the perf strip keeps its EMA for
  averages, but reports p95/max frame gap over a 1 s window (preallocated ring,
  rebuilt at the same 2 Hz, no allocation in the frame loop) and the event
  round trip split into its three phases, `events N (ms = dl a + cyc b + up c)`,
  plus the checkpoint push time. A single total cannot say whether a hitch is
  the queue drain or the JS.
- The frame loop counts frames the play path actually submitted, not the frames
  it asked for, so `steps/s` and `fps` describe the same frames.
- Every phase ends with the regression gate: `node tests/run-all.js`, the GPU
  parity ensemble (`node tests/gpu-parity.js 1000 --ensemble` over the headless
  rig) and a bench run compared against the previous phase's committed baseline.
  A phase that moves world evolution (event timing) must keep the release
  profile bit-identical or re-prove the long-run statistics; the parity ensemble
  is the arbiter.
- The JS side of the GPU engine runs headless: `tests/gpu-stub.js` is a stub
  device with real backing stores, so `tests/gpu-play.js` executes the mirror
  transfer and the play scheduling in `node tests/run-all.js`, and
  `experiments/roundtrip-cost.js` times them. No WGSL runs there — the kernel
  graph stays the browser rigs' job.
- Baselines are committed runs in `experiments/logs/`, named
  `0.3-<phase>-<description>.txt`. Existing: `0.3-1.txt` and `0.3-2.txt` (owner's
  rig, Phase I baseline), `0.3-phaseI-baseline-swiftshader.txt` (sandbox: no
  adapter), `0.3-II-roundtrip-cost.txt` (round trip before/after).

## Phase I — Instrumentation and baseline (done)

Goal was: make the suspects visible as numbers, then record the "before".

- **I1. GPU query sets in `GpuSim.frame`.** A timestamp query set resolves
  dispatch-group boundaries into a preallocated buffer, read back one frame late
  and folded into the 2 Hz strip as per-kernel GPU ms. Feature-detected, with a
  wall-clock fallback (`tsOn`). On the owner's rig: `tsCollect 1 ms · winners
  0.56 diagC 0.41 loserRank 0.29 diagA 0.26 ledgerReduceA 0.15`.
- **I2. Perf strip distribution stats.** Frame-gap ring + p95/max, the event
  round trip in three phases, the checkpoint push time.
- **I3. Bench, two modes, both time-boxed.** `bench.html` (standalone; also
  `index.html?bench=1`) and `experiments/gpu-bench.js` over the headless rig:
  step isolation (submit n frames, await `onSubmittedWorkDone`) and smoothness
  (the play path under rAF, median/p95/max gap and hitches > 2× median).
- **Baseline committed:** L5/L6 × 1/5 steps, dt 0.1 (`0.3-2.txt`):

  | level | steps | iso ms/step | smooth med | p95 | max | hitches | Myr/s |
  |---|---|---|---|---|---|---|---|
  | L5 | 1 | 8.900 | 5.6 | 111.1 | 122.3 | 33 | 6.3 |
  | L5 | 5 | 7.220 | 100.0 | 155.5 | 183.3 | 0 | 6.2 |
  | L6 | 1 | 21.500 | 16.6 | 405.6 | 472.1 | 9 | 2.1 |
  | L6 | 5 | 19.880 | 388.8 | 566.5 | 672.1 | 0 | 1.8 |

  The 20-step column of the matrix is still missing from the committed baseline
  and must be filled in by the next bench run.
- **I4. The smoke must not pass vacuously.** `webgpu-smoke.html` phase 4
  pixel-compares every layer against the CPU renderer; on the owner's rig it
  printed `mean|d| NaN max|d| 0 ch>16: 0` for all 16 layers — an empty
  comparison, which the old gate waved through because every NaN comparison is
  false. Now: a degenerate canvas, a short readback or a non-finite mean is a
  failure; the canvas/format/row are logged; and the renderer asks for
  `COPY_SRC` on the canvas (the spec's default canvas usage is
  `RENDER_ATTACHMENT` alone, so copying out of the current texture is not legal
  without it) via `GpuRenderer.init(state, { readback: true })`, leaving the
  app's usage untouched.
- **I5. Uncaptured WebGPU errors must carry their text.** The 32 errors in the
  baseline read `webgpu uncaptured: undefined` because the message lives on
  `event.error`, not on the event. Fixed; the next log names the actual
  validation errors.
- **I6. Open defect D1 — frame-5 plate speed divergence.** The smoke fails
  `meanSpeed drift > 20%`: cpu 4.022 vs gpu 4.947 cm/yr, maxSpeed 11.449 vs
  13.026, with owner mismatch 0/10242 and |dz| max 139 m, i.e. the states agree
  but the rotations do not. Measured on the CPU reference: frame 5 is 4.022 /
  11.449 (so the CPU side of the log is exact), frame 15 is 4.940, and the same
  cells evaluated with the *unrelaxed* `omegaTarget` give 5.040 / 13.052 —
  much closer to the GPU pair than any relaxation constant reproduces
  (forcing α = 1 gives 5.130 / 12.763). The working hypothesis is therefore that
  the device's ω follows the un-relaxed least-squares fit rather than
  ω + (fit − ω)·dt/τ_ω; it is not proven, and it cannot be settled without a
  device. The smoke now prints the discriminator on every run: the worst
  per-plate |ΔR·ω| and the CPU mean/max from both the relaxed and the target ω.
  Reading the code does not explain it: the relaxation is identical in
  `js/plates.js` and `wgsl-plates.js` `reduceB` (`omega + (fit - omega) *
  min(1, dt / tau_omega)`), `tau_omega` is 0.5 in both (`params.js` →
  `wgsl-common.js` `P_TAUOMEGA`), dt is 0.1 in both (`uploadFrame` → `fDT`), both
  engines boot with dt = τ_ω so both start at the fit, and the accessors agree
  (`plateOmega` = `PLATEF[p*8+1]`, `plateOmegaTarget` = `[p*8+2]`, written by
  `setPlateOmega`, read by `velocities`, contact and diag). Ruled out: a
  `prescribedOmega`/`fixedOmega` flag left set, a missing `reduceB` dispatch, and
  `velocities` reading the target slot.
  Gate: this must be explained (and either fixed or bounded) before the parity
  claim is accepted; the ensemble bound for mean speed is 20% and the frame-5
  transient is where it is tightest. The next capture carries the decisive
  number — each engine's own mean |ω|/|ω_target| — which separates "the device
  never relaxes" from "ω is fine and the aggregate differs".

Acceptance: per-kernel GPU ms visible at 2 Hz; baseline logs committed;
regression gate green; instrumentation < 0.1 ms/frame at L5 (measured 0.844
µs/frame of JS, `experiments/overhead-instr.js`). Still open: the 20-step bench
rows, a clean smoke run on the owner's rig, and defect D1.

## Phase II — The event round trip, made cheap (done on device; `dl` is what is left)

Goal: the event cadence stops being the frame hitch. The measured cause was the
transfer, not its position on the frame path, so the fix is the transfer:

- **One shared 4-byte cast buffer** for the f32-bits reinterpret. The edges
  block reinterprets twice per edge — 123k fresh `ArrayBuffer`s per transfer at
  L5, 491k at L6.
- **A light event mirror.** `GpuSim.EVENT_READS` / `EVENT_WRITES` carry only
  what `Events.cycle` reads and writes: columns, the plate table, the frame
  counters, plus `owner`/`cellPlate`/`relN`/`relT`/`edgeType`/`polarity` on the
  read side. Those cell and edge arrays are never written by the cycle (asserted
  by `tests/gpu-play.js`) and are recomputed by `raster`, `velocities`,
  `relatives`, `polarity` and `elevationZ` every frame, so shipping them back
  was cost with no effect. Checkpoints and on-demand syncs (probe, save,
  deposits, load) keep the full mirror.
- **Alive rows only**, with the alive flag past `n` zeroed so a row the device
  spawned can never be revived by a stale mirror.
- **Reused staging and pack scratch** (11 staging buffers and 4.79 MB of scratch
  per call before), with a fresh-set fallback when a probe download overlaps an
  event round trip.
- **`GpuSim.play(state, dt, n)`** is the play path's single entry point: n frames
  and their round trips in one call, the same device command sequence as n
  `step()` calls, returning the frames submitted. `step()` keeps its awaited
  contract for the parity harness and the single-Step button, and both share
  `roundTrip()`. Phase III turns `play`'s loop into one encoder.

Why the earlier "background the round trip" design was dropped, so it is not
re-proposed: awaiting a promise does not move JS off the main thread, so a
background task removes nothing from the frame gap; and a mirror that arrives
late reverts every frame the device ran in between, because the upload carries
the whole mirror — that is world corruption, not one cycle of latency.

Measured (`experiments/logs/0.3-II-roundtrip-cost.txt`, stub device, JS only,
min of 9 warm reps, before = commit c706442 under the same method):

| | L5 before | L5 after | L6 before | L6 after |
|---|---|---|---|---|
| download | 98.60 | 1.27 | 429.70 | 9.28 |
| `Events.cycle` | 2.15 | 2.09 | 7.84 | 7.92 |
| upload | 99.30 | 0.35 | 410.24 | 1.72 |
| **total** | **200.05** | **3.71** | **847.79** | **18.92** |

Result on the owner's rig (`experiments/logs/0.3-II-ondevice.txt`, nvidia/ampere,
Chrome 151, L5, 1 step/frame): frame 34.4 → 5.7 ms, p95 66.6 → 5.6 ms, max
77.9 → 11.1 ms, event round trip 114.7 → 31.7 ms, Myr/s 10.8 → 12.2 (CPU
reference: frame 11.3 ms, 9.0 Myr/s). The periodic lag is gone; the GPU now beats
the CPU engine on every distribution statistic at the same settings.

What the 31.7 ms is made of: `dl 29.4 + cyc 2.0 + up 0.3`. The JS half matches
the headless measurement, so what is left is the device — the queue drain plus
seven separate `mapAsync` round trips. `dl` still conflates the two, so the strip
now prints `dl A [wait W]`; if `wait` is most of it, the next step is one
combined staging buffer and one map instead of seven, or letting the drain
overlap the next submit.

The same capture exposed a defect the light mirror introduced and the stub had
not caught: `pull` unpacked by testing the staging *cache*, which keeps buffers
from an earlier, wider download, so a light event round trip called
`getMappedRange` on a `cellF` it had never mapped. The device raised
`OperationError: getMappedRange failed`, the play promise rejected, the loop
stopped, and the run stayed stopped until play was pressed — in the app the
trigger is any full sync (probe click, Save, deposit extract, or the 20 Myr
checkpoint) followed by the next event cycle, which is why runs died at a fixed
point in time. Fixed by unpacking only what the current transfer mapped;
`tests/gpu-stub.js` now enforces the map state and `tests/gpu-play.js` runs the
full-sync-then-event sequence, so the identical stack reproduces headless.

Acceptance (owner's rig, same configs as the Phase I baseline):

- The strip's event line shows a total ≤ 10 ms at L5 and ≤ 40 ms at L6, with the
  split telling whether what is left is `dl` (queue drain) or `cyc`/`up` (JS).
  **Not met yet**: 31.7 ms at L5, of which ~2 ms is JS. Re-test after the `wait`
  split says which device cost to attack.
- p95 frame gap ≤ 2× median while playing at dt 0.1, 1 and 5 steps/frame, for a
  ≥ 200 Myr hot-start run that includes split and suture activity.
- Throughput at 1/5/20 steps ≥ baseline; the bench re-run fills in the missing
  20-step rows.
- Parity ensemble green and the release profile statistics unchanged. The
  light mirror changes *what* is transferred, not *when*, so the device command
  sequence is untouched and same-device runs must stay bit-identical.

## Phase III — Diagnostics off the frame path (0.5–1 d)

Goal: stop paying for numbers nobody reads every frame. The on-device kernel
table puts `diagA` 0.98 ms and `diagC` 1.69 ms — 2.67 ms of the 6.74 ms top-10
total at L5, ~40% — in the K11 diagnostic passes, and nothing on the device
reads their output: `diagA`/`diagC` write only the `reduce` scratch, `diagB`
folds it into the `diag` buffer, and that buffer is read only by the CPU mirror
(`meanSpeed`, masses, `oreSum`, `gaps`, `quatError`, `rigidError`).

Consumers, which set the cadence:

- `js/ui.js` shows `state.meanSpeed` in the status line, refreshed on a ~150 ms
  tick — so ~6 Hz, not 60–180 Hz.
- `GpuSim.download` (full mirror) copies `diagOut`; the light event round trip
  does not touch it.
- `tests/gpu-parity.html` and `webgpu-smoke.html` compare `meanSpeed` after an
  explicit download, so a full download must be preceded by a diagnostic frame.

Design: `GpuSim.frame(state, dt, diag)`; `play` runs the three passes only when
the HUD has asked for fresh numbers since the last diagnostic frame, or when the
frame is followed by a full round trip. `step` keeps them on every frame so the
parity harness is untouched. `zeroFrame` already clears the accumulators each
frame, so an on-demand pass reports that frame's values, not an accumulation
over the skipped ones.

Acceptance:

- L5 kernel table shows `diagA`/`diagC` absent on non-diagnostic frames, and the
  step-isolation ms/step falls by roughly their share (~2.5 ms of ~8 ms).
- `meanSpeed` in the status line and after any full download is the current
  frame's value; parity harness and smoke unchanged and green.

## Phase IV — N steps in one command buffer (1 d)

Goal: the per-step fixed cost (encoder + submit + `uploadFrame` write + JS) is
paid once per rAF, not once per step. On this rig that is ~1.1 ms of an 8.7 ms
step at L5 (7.6 at 5 steps), so the expected win is ~13% at 1 step/frame — worth
taking after the diagnostics phase, not a rescue.

- `GpuSim.play` precomputes n `frameIn` blocks on the CPU before encoding: the
  mantle bookkeeping (`Tm`, precession, plume spawns, wave phase) is sequential
  and cheap, and keeping it on the CPU is the design's split. `frameIn` becomes
  n×74 floats (the buffer grows with the max n, 20); one encoder carries n× the
  dispatch list of `frame()`, one submit.
- Same dispatch order and same input values as n separate `frame()` calls, so
  results must stay bit-identical on the same device: the parity harness and the
  frame-2 clone test are the checks (the clone test specifically catches "same
  numbers, wrong decision path" drift).

Acceptance:

- GPU ms/step from the step-isolation bench flat across 1/5/20 within 10%.
- Parity harness: same-device bit-identical; ensemble green.

## Phase V — `loserRank` without the O(losers × n) scan (0.5–1 d)

Goal: turn the only superlinear kernel into a bounded one. Measured share at L5
on a saturated queue: 1.09 ms, ~16% of the top-10 kernel time (0.29 ms and ~4%
when the queue was still stalling on the event round trip); the heavy-overlap
epoch is worse still.

- Losers are already binned per winner (`loserCount` + `scanC` offsets).
  Rewrite as one workgroup per winner: load the winner's L_w bin entries into
  workgroup memory, compute each entry's rank by index (L_w²/2 local
  comparisons, trivially parallel in the workgroup), write `loseList`.
  Worst case is one giant winner (L_w ~ colCap during a mega-collision):
  chunked workgroup memory handles it; typical L_w is single digits.
- The rank definition (index order among a winner's losers) is unchanged, so
  the output list is identical — a bit-identical refactor, proven by the parity
  harness.

Acceptance:

- Contact-block GPU ms (I1 query sets) reduced ≥ 5× in a heavy-overlap rig — a
  new `experiments/` config that maximizes per-frame overlaps (e.g.
  `plateCount 4`, low `vSuture`, hot start) with the overlap count logged from
  the frame counters to show the load was real.
- Parity: same-device bit-identical; ensemble green.

## Phase VI — Polish and L6 (1–2 d)

- Merge the render pass into the play encoder: one submit per rAF for sim + draw
  instead of two (acquire the canvas texture, append the render pass after the
  compute passes in `play`).
- UI: level select (L5 / L6, L6 offered on the GPU engine per the "CPU JS first
  (L5), then WebGPU (L6–L7)" policy) and an event-cadence select (1 / 5 / 10
  Myr) as the user-facing fast-forward escape hatch; default stays 1 Myr so the
  canonical run is unchanged.
- Bench matrix extended to L6 (both modes, 1/5/20 steps); L6 baseline committed.

Acceptance: L6 playable at 1–5 steps/frame with p95 ≤ 2× median on the
calibration host's hardware; SwiftShader numbers recorded as relative only
(existing convention). All earlier gates still green.

## Risks and how the plan handles them

- **The light mirror ships too little.** The claim is narrow and asserted:
  `Events.cycle` writes only the columns, the plate table and the counters, and
  the frame kernels recompute every cell and edge array it reads before anything
  reads them. `tests/gpu-play.js` fails if a cell or edge buffer survives an
  event round trip written, and the parity ensemble plus the release profile are
  the arbiters on device.
- **Query-set portability** (missing on some SwiftShader builds): feature
  detect, wall-clock fallback, and the headless rig documents the flags.
- **Event staleness changing long-run statistics:** the cadence is never skipped
  (`play` runs the same round trips in the same order as `step`), `Events.cycle`
  is span-aware and gets the span of the due date, and the gates are the parity
  ensemble plus the release profile; any statistics drift is a plan failure, not
  a tunable.
- **N-step encoder breaking parity:** bit-identity is an acceptance criterion,
  checked by the frame-2 clone test and the 1000-frame ensemble before the phase
  is closed.
- **Bench on the wrong device:** every reported number carries its device string
  (adapter info at boot); SwiftShader is labeled relative-only, matching the
  existing BENCH convention in the sibling project.
- **Defect D1 hiding behind a passing ensemble:** the ensemble samples every 10
  frames, and the frame-5 transient is exactly where the mean-speed bound is
  tightest. The smoke's discriminator line is the standing check.
