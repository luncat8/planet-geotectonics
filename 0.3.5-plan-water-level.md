# 0.3.5 — Water level plan: display eustasy, level and volume controls

Implements the 0.3.5 draft (kept verbatim below): a slider that recolors the map, and a
second control for the volume view — *level* (fast, direct) and *volume* (conserve water,
incompressible — the level is derived from a conserved volume, not set). The control shape is
**two sliders, no checkbox**: the last slider the user touches enables its mode and greys the
other (the 0.3.5 review decision — the quantity pair is not a dual of one slider, and a mode
bit is the redundancy this row exists to remove).

> slider level → map colorize
> checkbox switch level (fast) / volume (conserve water, incompressible, dont need
> recalculate every frame, think is this costly)

## 0. Scope: display eustasy, the sim stays untouched

The sim's sea level is the calibrated `0`: the erosion intake's `z > 0` gate
(`Surface.route`, `wgsl-surface` erode), the turbidite 50 % pass-through (`wet`), the basin
potential's `wet` gate, and the re-calibrated 0.3.3 release history all sit on it. Making
the sea level a physics parameter would be a calibration change requiring the full
re-proof (the 0.2/0.3 convention), and the design files eustasy as backlog (§12). The
draft's own first line says what the control is for: **map colorize**. So:

- the sea level is a renderer-only global, exactly the class of 0.3.3's Relief range:
  live on both engines, mid-play, no restart, and the default (level 0, level mode) is
  bit-identical to today's rendering;
- the sim keeps `wet = z < 0`. The display level `Params.sea` (m, default 0) is the single
  source of truth for what is drawn and for the probe's wet/land label;
- 0.4.0 (an Earth heightmap with its own ocean level for proper colorize) and 0.5.0 (the
  3D water shell's radius) ride this same scalar. This plan is the mechanism, not a world
  change.

Two ways to name the level:

1. **Level mode** (default, "fast"): the slider sets the level directly. Cost is the
   Relief range slider's cost (0.3.3 §4): one f32 in the draw uniform (GPU) or one module
   global (CPU, `RenderParams.sea`). No histogram, no solve. A drag writes `Params.sea`
   and sets `dirty` so the recolour is explicit on both engines.
2. **Volume mode** ("conserve water, incompressible"): the slider sets the total water
   volume as a multiple `×` of `V0` — the volume that fills the seafloor at level 0. The
   level `L` is then solved so that an incompressible body of exactly `×·V0` fills every
   bit of seafloor below `L`. The volume is the conserved quantity; the level is derived.
   So when the bathymetry changes (an ocean opens, shelves erode, an orogen sinks), the
   level moves to keep the volume constant — emergent eustasy for the display, for free.

## 1. The volume solve — the answer to "is this costly?"

Recomputing the level = a hypsometric histogram of the V cells' `z`, plus a 1-D solve of
`V(L) = target`.

**Histogram.** `NB = 512` buckets over the fixed interval `[zLo, zHi] = [−15 km, +15 km]`
(`w = 60 m`; world `z` past the interval clamps into the end buckets — the calibrated
history's range is −8.7…+6.2 km). Each bucket holds `N_k` (count) and `M_k` (Σz). Gap
cells (NaN `z`) are skipped: no crust, no seafloor, no water volume.

**Solve.** For a level `L` in bucket `k` (`L = zk + f·w`):

```
V(L) = Σ_{j<k} N_j·(L − M_j/N_j) + N_k·w·f²/2
```

Fully filled buckets are exact (first moment); the intra-bucket term assumes the seafloor
is uniform inside its 60 m, bounded error `N_k·w²/8` — three orders below one cell's
volume at L5. Given a target `V`, a 512-add prefix walk finds `k`, then one quadratic in
`f` (the empty-bucket case is linear):

```
a·f² + b·f − Δ = 0,   a = N_k·w/2,  b = w·Σ_{j<k} N_j,  Δ = V − (Σ_{j<k} N_j·zk − Σ_{j<k} M_j)
f = (−b + √(b² + 4aΔ)) / 2a,   clamped to [0, 1]
```

No iteration, deterministic, the same arithmetic on both engines. `V0 := V(0)` is
measured the same way and rides out with the level.

**Cost — the actual answer.** The rebuild is `O(V)`: the JS histogram is ≈ 0.3 ms at L5,
≈ 1–2 ms at L7 (V = 163,842, f64); on the device it is one atomic-add dispatch over V
threads plus a 1-thread solve, ≈ 0.2 ms at L7 on hardware — the same class as the 2 Hz
`tsCollect` timestamp pull the HUD already runs. **It is not costly, and it is not needed
per frame in the first place:** the seafloor moves on tectonic times (isostasy is Myr; a
frame is 10–100 kyr), so a per-frame solve would buy a level accurate to one frame of
coastal drift — invisible at any camera, while paying O(V) at the one rate that actually
matters. What the world's volume needs is a tracking cadence, and the drift between
cadences is bounded by the tectonic Δz of the coastal band (sub-meter over 500 ms at
calibrated speeds). So the cadence is:

- **on input** (slider drag): the input only arms `seaDirty`; the frame loop solves at
  most once per rAF (input events fire faster, and the solve is deferred to one place on
  both engines — a 2 ms L7-CPU drag cannot eat the event handler);
- **on the 2 Hz perf tick** (the Tm follower's tick) while the volume slider is the active
  control, to track bathymetry drift while playing;
- **never per frame.** The per-frame version is the `O(V)` above — ≈ 0.1 % of the frame
  budget at L5, ≈ 2 % at L7: affordable, buying nothing, so it stays reserved as the
  upgrade path. If a future level (L8, 655k cells) ever demands it, the histogram becomes
  incremental — the elevation pass moves each cell that crossed a bucket boundary between
  buckets, `O(V)` comparisons, no allocation — and the interval, bucket algebra and solve
  above are already the same.

**Precision.** The GPU histogram is f32 `z`, the CPU's f64: a `z` within a ulp of a 60 m
boundary can land in the neighbour bucket, shifting `L` by ≤ `w`. The level is a display
quantity (map coastlines, the 3D water shell's radius), so this is pinned as a tolerance
(≤ 60 m, same floor class as the other parity tolerances) — never a bit-identity claim.

## 2. Where the level lives, and who reads it

`Params` (global settings that carry across a rebuild, like `zRange`; **not** checkpoint
state — no VERSION bump):

- `Params.sea` (m, default 0) — the display sea level. Single source of truth for the
  renderers and the probe.
- `Params.seaVolScale` (×, default 1.0) — the volume-slider value; the target is
  `seaVolScale · V0`. (No mode field: the active slider is UI-enable state, not a Params
  key — there is nothing to report or pre-fill, and the defaults of the two sliders already
  agree so either one reads 0 at first paint.)

The solver module `js/water.js` (new) owns the writes to `Params.sea` in volume mode
(input's rAF and the 2 Hz tick); in level mode the slider's `input` writes it directly,
exactly as `applyAdjust` writes `zRange` today. Renderers read only `Params.sea`:

- **CPU Renderer** (`render.js`, z branch): `z < 0` becomes `z < sea`, and the 0.3.3
  relief ramp goes sea-relative so the shore band of width `zRange` moves with the level
  (land saturates at `sea + zRange`, the deep floor at `sea − zRange`):

```
water:  shallow = max(0, 1 − (sea − z) / zRange)
land:   high    = min(1, (z − sea) / zRange)
```

- **GPU 2D** (`render-gpu.js`): `struct U` gains one f32 `sea` — offset 36, the struct
  stays 40 bytes in the 48-byte buffer (the 0.3.3 `zRange` mechanism verbatim, no
  reallocation, no pipeline rebuild). The z branch of `cellColor` tests `z < u.sea` with
  the same sea-relative ramp. The uniform is written per draw from the last resolved
  `Params.sea`; a volume-mode drag therefore lags the slider by the solver's async pull,
  ≤ 2 frames — imperceptible, and the paused redraw goes through the same drained-queue
  path.
- **Probe** (`ui.js`): the wet/land label and the depth readout compare against
  `Params.sea`, so the inspector never disagrees with the drawn coast.

A level drag on the GPU engine writes `Params.sea` and `dirty`, never `state.z`: the level
is a uniform, the volume solve is a device-side histogram — neither one reads the play
path's mirror.

## 3. Volume mode on the GPU engine — no readback on the play path

The play path never reads state back, so the histogram and the solve run on the device:

- Buffers (one-time, in the `GpuSim` session arenas so a level switch releases them):
  `seaHist` (512 × 2 f32: `N`, Σz) and `seaOut` (4 f32: `L`, `V0`, ocean area, `V`).
  Zero-initialized → `L = 0` = the default rendering is valid before the first solve.
- Kernels (a display-only WGSL module, read-only on `cellF.z`, pinned by
  `tests/wgsl-struct.js`):
  - `seaHist` — V threads, one atomic add into the bucket of `z` (NaN skipped). Preceded
    by a 1 KB zero (the atomic path's precedent is `zeroFrame`);
  - `seaSolve` — 1 thread: the §1 prefix walk + quadratic, writes `seaOut`.
- Cadence and plumbing: both ride a small standalone encoder — **never inside the sim
  segment** (the hot path stays slim, and the sim graph is bit-identical by
  construction). It is dispatched from the frame loop on `seaDirty` (coalesced input) and
  from the 2 Hz tick in volume mode. After it, a fire-and-forget 16-byte `mapAsync` pull
  (the `tsCollect` pattern: async, never a main-thread stall — the play path already
  drains the queue per segment, so the pull waits behind at most one segment) updates
  `Params.sea`, the readout and the 2D uniform.
- Boot: the boot solve (zero + hist + solve) rides the boot raster's own encoder,
  appended after `elevationG` where `z` is already final — one extra submit at most, so
  the first volume-mode tick and the first 3D frame (0.5.0) see a valid `V0`. A paused
  world's input solve uses the existing drained-queue redraw ordering.
- CPU engine: the JS solver in `js/water.js` reads `state.z` directly — no device, no
  queue, no pull. The same coalesced-per-rAF cadence applies (bounded ≤ 2 ms at L7,
  sub-0.5 ms at L5/L6). The CPU path is also the node test path — no adapter needed.

## 4. UI (Adjust group), last-active enable, capture

After the Relief range: a **Sea level** slider (km, −10…+5, step 0.1, default 0.0) and a
**Water ×** slider (0…4, step 0.05, default 1.00). No checkbox: **the last slider the user
touches enables its mode, and greys the other** (`title` text: `Level` / `Volume`). The
level slider is the default active on a fresh page, so the default world is drawn in level
mode exactly as before. Two controls, two permanent meanings and two permanent scales — one
meaning per control, no label flipping.

- **Enable, not flip:** there is no mode event, so there is nothing to make continuous and
  no mode to report. The two defaults already agree (level 0 ≡ 1.00×), so whichever slider
  is enabled at first paint the coast is the same. Touching the volume slider solves
  `seaVolScale·V0` for the first time; the level slider keeps its direct write.
- Readouts (fixed-width, tabular, rewritten on the 2 Hz tick with the Tm follow): level
  `+1.2 km`; volume `1.50× · +0.4 km` — the solved level is always shown, because it is
  the quantity the map actually uses. The inactive control's readout stays where it is,
  dimmed with the slider.
- Clamps: `× = 0` → `L = zLo` (a dry planet, readout `dry`); `×` past full submersion →
  `L = zHi` (readout `flooded`). The slider range 0…4 comfortably brackets both on the
  calibrated worlds.
- Capture header (non-default only, the copy-header policy): `sea +1.2 km` or
  `sea vol 1.5× (+0.4 km)` — whichever slider is active, so a log line still names the
  control that produced the world.
- URL pre-fill: `?sea=1.2` or `?seavol=1.5` (the active slider is inferred from which value
  is given; both given is a level-over-volume tie broken in favour of the level slider) —
  deliberately **not** `?level=` (that is the Resolution select); out-of-range values are
  ignored, like every other pre-fill.
- The sea setting is a page global: a rebuild (level change) and a Load carry it over,
  exactly as the other Params knobs do — and a world change re-arms `seaDirty`, so the
  next tick re-solves against the new bathymetry.

## 5. Tests

- `tests/water.js` (new, node, no adapter): the solver on hand-built hypsometries —
  monotone `V(L)`; `V(0) = V0` identity; a flat seafloor sitting exactly on a bucket
  boundary (the quadratic is then exact against the analytic fill, to 1e-9) and one not
  aligned (error ≤ `N·w²/8`); NaN gaps skipped; the clamps at `× = 0` and past full
  submersion; the empty-bucket linear branch.
- One source for the constants: `tests/wgsl-struct.js` pins `seaHist`/`seaSolve` —
  balance, entry points, and `zLo`/`zHi`/`NB` against the JS module they are baked from.
- `tests/gpu-play.js` (stub device): the solve encoder is exactly three dispatches (zero,
  hist, solve) plus the 16-byte pull; the buffers live in the session arenas (released on
  a level switch — the 0.3.4 leak lesson); a solve is never appended to a segment encoder.
- `tests/gui.js`: the two sliders sit in Adjust, the level slider active by default;
  touching a slider enables it and greys the other (the last-active rule); `?sea=1.2` and
  `?seavol=1.5` pre-fill, each activating its slider; the header line only when
  non-default; the level slider sets `dirty` on the CPU (recolour) and the volume solve's
  pull lands in `Params.sea` (the stub records the bytes) and in the GPU uniform on the
  next draw; the probe's wet/land follows `Params.sea`.
- Smoke (`webgpu-smoke.html`): the layer sweep runs the z layer at a non-default sea on
  both engines — the pixel parity holds (both engines recolour identically); the volume
  solve's CPU-vs-GPU `L` on the same L5 world: |ΔL| ≤ 60 m.
- Gates: the short profile green; the sim ensemble and the bench are **unchanged** — no
  sim kernel and no sim parameter is touched, which is the point of the display-only
  scope (the acceptance profiles stay bit-identical).

## 6. Order and acceptance

Order: (1) `js/water.js` + the `render.js` z branch + the probe — the CPU engine complete
in isolation; (2) the GPU side: `seaHist`/`seaSolve` + the draw uniform + the tick/input
plumbing + the boot solve; (3) UI: sliders, last-active enable, readouts, header, URL; (4)
tests + the smoke section.

Acceptance:

1. Live on both engines, mid-play, no restart, no measurable stutter: the sea recolours
   within 2 frames of the input; ms/step within the bench noise (the sim graph is
   untouched).
2. Default (level mode, sea 0) is bit-identical: z-layer pixels unchanged, ensemble
   unchanged, bench unchanged.
3. Volume mode: a drag re-solves at most once per rAF; the 2 Hz tracking keeps the
   coastline honest while playing; the 2 Hz cost is ≤ 2 ms at L7 on the CPU (measured)
   and the GPU solve + pull ≤ 0.3 ms at L7 on the rig (measured); the readout always
   shows the solved km.
4. Last-active enable: touching either slider switches the active control with the coast
   already continuous by construction (both defaults are level 0), and `× = 0` and
   `× = 4` clamp gracefully with the named readouts (`dry` / `flooded`).
5. Checkpoints unchanged (no VERSION bump; a v2 blob loads and the sea setting carries
   over as a page global, like `zRange`); the header + URL reproduce the sea setting from
   a log line alone.
6. Downstream plans consume this without new machinery: the 0.5.0 3D water shell is
   `R + exag·Params.sea`, and the 0.4.0 Earth map's ocean level is a `?sea=` pre-fill.
