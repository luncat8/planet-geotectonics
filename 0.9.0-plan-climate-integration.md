# 0.9.0 — Plan: climate integration with `planet-climate` (planning artifact)

Keep the globe's current work compatible with a future climate engine integration. This plan
does **not** schedule climate implementation and nothing in 0.8 waits on it. It records what the
counterpart is, what each side should borrow, the two-clock architecture, the field seam in both
directions, the project structure, the threading verdict, and the short list of rules that
current increments must keep so the integration stays possible.

Source review basis: `luncat8/planet-climate` main (WebGL2 engine, `planet/`), its
`40-improvement-plan-webgpu.md` (including its own cross-borrow §7), `AGENTS.md`, `README.md`
and the module notes `CO2.md`, `CRYOSPHERE.md`, `OCEAN_MASS.md`. The request that opened this
line is `0.9.x-draft-climate-integration.md`.

## 1. What planet-climate is today (facts)

| aspect | climate (`planet-climate`) | globe (this repo) |
| --- | --- | --- |
| render/compute | WebGL2 fragment passes, 8-texture state codec, ice in its own ping-pong pair | WebGL render + WebGPU compute (L6-L7), no-readback renderer |
| grid | icosahedral dual-hex, same lineage; `V/W/H` verified equal to ours at L3 (642/256/3) | icosahedral dual-hex, L0-L7 |
| time | dynamics `dt` in seconds (default 60, cap 900) with adaptive substeps 1-128 per frame; `simTime` in days | crust step 10k-100k yr, dt-insensitive kernels |
| slow variables | carbon cycle + biomass as CPU ODEs on a *geological clock* (`P.geoYears`, `co2Speed` years per physics step) incl. Milankovitch forcing | geology itself |
| persistence | plain-JS save `planet_state.js` (base64 of 8 textures), auto-loaded, `file://` friendly | binary checkpoints |
| harness | headless `harness/`, equilibrium-save testing culture | node `tests/run-all.js`, experiments, logs |
| module hygiene | classic scripts, **no guarded `module.exports`** in `planet/*.js` | guarded everywhere, node-loadable |
| scaling plan | its own WebGPU port plan (`40-improvement-plan-webgpu.md`) with a cross-borrow §7 | — |

The mesh audit found: same subdivision scheme, equal topology dimensions at equal level, but the
files diverged (different buffer layouts, ocean-bathymetry options, radius conventions). Cell
**index equality across the two `geodesics.js` files is plausible but unproven**; treat mapping
as by-direction until the audit below passes.

## 2. Engine/GUI comparison verdict

The counterpart already maintains the borrow list in both directions
(`40-improvement-plan-webgpu.md` §7). This plan adopts that list by reference and only rules on
priority and on what must **not** merge:

- Borrow into the globe (from §7, globe side), priority order: the plain-JS `file://` save
  complementing checkpoints; the `bench.html` standalone-GUI conventions (batch-averaged timing
  with stated resolution, device header, copy-log); per-parameter `tip` metadata; the
  particle-tracer flow-viz for mantle presentation (deferred-0.5.7/0.7.x territory, not now).
- Recommend to the climate agent (from §7, climate side), priority order: parity-with-tolerance
  methodology and committed baseline logs; bounded-kernel audit applied to its serial O(V)
  reductions and fixed Jacobi counts; event-cadence readback discipline; checkpoint ring with
  validated single-blob persistence; findings/pitfalls document.
- Add to the climate recommendations (gaps its §7 does not list): add guarded
  `module.exports` to every `planet/*.js` so node harnesses can load them (prerequisite for any
  shared audit tooling); document dt-sensitivity per pass like the globe's kernel contract; keep
  WebGL2 until its own WebGPU plan lands — do not adopt the globe's WGSL structure wholesale,
  the pass shapes are different; adopt the tab/LF single-style rule.
- Do **not** merge: the two engines stay separate simulations in separate repositories. No
  shared `geodesics.js` (they diverged; a shared copy would freeze one side's bugs into the
  other). No engine vendoring in either direction. Climate's ocean/air state and the globe's
  crust are never one dataset.

## 3. The two clocks (the core design)

Two independent simulation clocks advance in the same page, at their own natural strides:

| clock | owner | stride | advanced by |
| --- | --- | --- | --- |
| geological | globe crust | 10k-100k yr per pass (existing) | user action or a slow cadence |
| climate dynamics | climate engine | seconds-minutes per substep, a bounded substep budget per animation frame | every animation frame while unpaused |

They are never synchronous: one 10 kyr crust pass would need ~10^6 climate substeps. Instead the
coupling is asynchronous by construction, which is the standard pattern for coupled
different-timestep models:

- crust reads **climate means over the crust step window** (area-weighted temperature,
  precipitation, ice/snow cover), never instantaneous weather. Forcing enters as a step
  function held for the whole pass — this is exactly what the kernels' dt-insensitivity
  contract (10k-100k yr) already tolerates;
- climate reads **crust state at crust-step boundaries** (topography, land/ocean mask, sea
  level) and holds it constant between boundaries — weather evolving over a staticEarth snapshot
  is the correct behaviour at climate timescales;
- climate's own slow variables (carbon, cryosphere volume) already run on a geo-clock
  (`P.geoYears`); they are the third, implicit clock and stay owned by the climate engine. When
  0.9.3 arrives, tectonic CO2 outgassing feeds that clock; it does not bypass it.

Pause rules (from the draft): each engine has its own pause. A paused globe keeps weather
running on the current surface (a legitimate view); a paused climate freezes weather while
geology continues; both paused is a still image. Display shows both clocks explicitly
(`t = 212.4 Myr · weather day 148`).

## 4. The field seam (both directions, v0)

| direction | fields | cadence | notes |
| --- | --- | --- | --- |
| globe → climate | per-cell surface elevation `state.z` (m), land/ocean mask, effective sea level | at each crust-step boundary, on demand | exactly the authoritative surface split; no crust internals, no plate ids, no potentials |
| climate → globe | per-cell means over the coupling window: surface temperature, precipitation, snow/ice cover; plus global means (meanT, SST mean, ice fraction, CO2 when the carbon cycle is on) | windowed mean aligned to crust steps | consumed only by named surface params (erosion/weathering/eustasy candidates), never written into crust state |

Mapping rule: map by direction through each side's nearest-cell lookup raster; do not assume
`index == index` across the two repos until the audit below proves it. Units are SI metres;
both sides already keep an equirect `lookup/lookupW/lookupH` raster, which is the cheap shared
currency. Ownership is absolute: climate never writes crust fields, the globe never writes
ocean/air state — the only allowed globe-side consumers are named scalar/field params in the
surface kernels.

## 5. Project structure

- Three repositories stay three repositories. Shared code only via the 0.8.0 pattern: a tiny,
  pure, byte-identical `port/` file with a hash gate — and only when a concrete shared need
  appears (the only near-term candidate is the grid-compat audit helper of §6). Speculative
  sharing is how drift starts; 0.8.0's rule (share only a small pure protocol with a manifest)
  is the standing answer to the draft's "how better to keep files and git projects".
- Hosting: the globe page hosts the climate engine as a library, the same way the slice's
  0.9.0 draft hosts its column engine (its C1): classic script tags, one global per file
  (`Climate`), `autoStart=false` so the host owns frames — the climate engine already has that
  hook. The climate page stays standalone and never vendors the globe.
- During development the host page loads the sibling checkout by relative path; a release
  vendors a copy recorded in a provenance note (the `vendor/` convention). No submodules, no
  network, `file://` always works.

## 6. Multithreading verdict (the draft's question)

Under `file://` the honest answer is: no CPU worker architecture.

- `SharedArrayBuffer` needs COOP/COEP headers, which a `file://` page cannot set — so
  shared-memory workers are unavailable in the environment both projects target;
- transfer-by-`postMessage` workers copy: a world mirror is tens to hundreds of MiB of typed
  arrays, so per-frame transfer would swamp the copy and the GC; worker *scripts* from
  `file://` are additionally blocked in Chromium (only `blob:` workers work);
- the practical second thread is the GPU: WebGPU compute is async, and the globe already runs
  device kernels with the event-cadence readback discipline. The performance limiter is the
  CPU core count on the CPU path (why the GPU path exists) and dispatch/readback cadence on the
  device path — not a missing worker pool;
- allowed worker uses, if ever measured to pay: setup-time builds outside the frame loop (e.g.
  the heightfield lookup build), capture/bench encoding, headless bakes. None in the frame
  loop. Revisit only with a measured bottleneck and a `file://` proof in both browsers.

The same verdict applies to the climate engine; its WebGPU port plan is the right scaling
direction there.

## 8. Keep-compatible rules for current work

The only part of this plan that binds increments **now**:

1. keep `state.z` the authoritative elevation in metres and water settings one owned block —
   they are the entire globe→climate surface contract;
2. keep kernels dt-insensitive within 10k-100k yr; climate forcing will arrive as step
   functions held for a whole pass;
3. keep cell centers, `ring` and the `lookup` rasters public and stable — the mapping depends
   on them;
4. route any new erosion/weathering/eustasy constant through named params (`js/params.js`),
   never inline magic numbers — the seam replaces params, not kernel structure;
5. keep the checkpoint format versioned and extendable so a climate sub-state can join without
   a format break; clocks travel separately, each with its own version;
6. keep the event-cadence readback discipline; any climate global-mean reduction on the device
   mirrors it;
7. never put display/projection state into simulation state — climate is another renderer of
   the same world;
8. keep every engine bootable headless and node-loadable (guarded `module.exports`);
9. register each new page global as one object (`Slice`, `Resolution`, … pattern); climate adds
   `Climate`, never loose globals;
10. the six ore potentials and the deposit catalogue remain globe-local; the carbon cycle uses
    its own fluxes and consumes none of them.
