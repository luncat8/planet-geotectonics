# 0.3.5 review — the implemented water-level controls, and the 0.4.0 / 0.5.0 plans

Review of the last commit (`34b6a68`, "Implement 0.3.5 display water level controls"), the
control-shape question it raised, and the two dependent plans `0.4.0-Earth-map-plan.md` and
`0.5.0-plan-3d-render.md`. Decisions here are already applied to the plans; this file is the
reasoning plus the tracked implementation items.

## 1. The implemented controls

The commit ships three controls in Adjust: a **Sea level** slider (−10…+5 km), a **Water ×**
slider (0…4), and a **Volume** checkbox that switches which slider is live. `tests/water.js`
passes, the solver `js/water.js` matches its plan §1, the renderers read `Params.sea` on both
engines, and the default page is bit-identical (sea 0 → the sea-relative ramp reduces to the
0.3.3 ramp verbatim). This section reviews the mechanism, §1.1 decides the control shape, and
§1.2 records what the code still owes.

### 1.1 Decision: drop the checkbox — 2 sliders, enabled by last touch

Keep both sliders, remove the checkbox, and let the last slider the user touched pick the mode:
the other greys until touched. This is the "2 sliders, enable by last active" of the three
options.

The three-control arrangement violates the plan's own rule, stated in 0.3.5 §4:

> one meaning per control, no label flipping

A checkbox labelled "Volume" and a slider labelled "Water ×" only carry meaning because the
other exists: the checkbox is a pure mode bit, the volume slider is dead weight in level mode,
and the level slider is dead weight in volume mode. Two of the three slots are conditional on
the existence of the third — the redundancy this review was asked to settle. A mode control also
costs a row and a readout for a knob a user flips once a session.

The "1 slider + toggle" alternative is worse, because the two quantities are not duals of one
another:

- **Level** is a direct, calibrated display offset in metres — `Params.sea`, the scalar the
  renderers, the probe and (in 0.5.0) the water shell read directly.
- **Volume** names a *conserved* quantity (× of `V0`); its level is *solved* out of the
  hypsometric histogram. It is a different axis, with a different range, step and readout
  (`1.50× · +0.4 km`, not `+1.2 km`).

One slider + a toggle would have to relabel itself between "Sea level (km)" and "Water ×",
giving up the always-visible mode-independent readout of two native scales, and a mode switch on
one thumb cannot stay coastline-continuous across two differently-scaled ranges. Two sliders,
each with a permanent home and a permanent scale, is the cheapest correct reading of the draft's
"switch level (fast) / volume (conserve)" as a *control behaviour* rather than a *state*.

What last-active-mode costs, and why that is fine:

- no mode flag to report — the capture header stays `sea +1.2 km` (level) or `sea vol 1.5×
  (+0.4 km)` (volume), and the URL pre-fill drops the `seamode` token;
- no flip event, so no continuity algebra (`switchWaterMode` presetting the volume slider) and
  no mode-switch test — the two defaults already agree (1.00× ≈ level 0), so the default coast
  is identical whichever slider is active;
- the enable bit lives beside the controls, like the existing `slow` flags, and one focus/
  pointer handler arms it.

The solver, cadence, precision tolerance, GPU story and calibration arguments of plan §0–§3 are
untouched: this only shrinks the UI surface.

### 1.2 Findings in the code (independent of §1.1)

1. **Level drags never set `dirty`, so the CPU engine never recolours.** `solveWater` (ui.js)
   writes `Params.sea` on the level path and then calls only `paintAdjust` (readouts, the
   disabled-state juggling) — no `dirty = true`. The CPU draw in the frame loop runs on
   `dirty || viewMoved`, so a sea drag never reaches `renderer.draw`: the readout changes, the
   map does not, until some unrelated step sets `dirty` (a sim advance, a layer switch). On the
   GPU engine it happens to survive because draw/redraw paths are different, but the write is
   still implicit. Make the intent explicit: the level path writes `Params.sea` **and** sets
   `dirty = true`, exactly as a Relief change sets `dirty` on a `zRange` change.
2. **Volume solves re-solve on the 2 Hz tick.** The body of `solveWater` should be reached from
   the tick only while the volume slider is the active control (the plan's "while volume mode is
   on", reworded for §1.1), never in the sim hot loop. All good — no write of `Params.sea`
   happens outside `solveWater`.
3. **A mode flag leaks into the capture and the URL.** `seamode=1` / `sea vol …` presuppose a
   persistent mode bit; with last-active-mode they go. (The 0.4.0 plan's §3 URL line for the
   sim's own `level` is untouched — `level` is already the Resolution select, not a sea token.)
4. **The GPU uniform already ranges `sea`.** `zRangeWord = new Float32Array(uniformBytes, 32, 2)`
   and `zRangeWord[1] = GpuRendererParams.sea` ride the 48-byte `U` struct as planned (offset 36),
   so sea must be written wherever an engine writes zRange — the two moved together in 0.3.3 and
   must continue to. Noted, no change.
5. **The GPU volume solve never needs `state.z`.** The plan commits the histogram + solve to a
   standalone side encoder with a fire-and-forget 16-byte pull (the `tsCollect` pattern) — a level
   drag stays direct even in volume mode; the device solve writes `seaOut`. The JS solver covers
   the CPU engine and the GPU between-batches path. Recorded, not changed.

### 1.3 Verified

- `node tests/water.js` → PASS.
- The solver's quadratic (`a = inBin·WIDTH/2, b = count·WIDTH, f = (−b + √(b² + 4aΔ))/(2a)`) is
  the plan's §1 equation with the two tightening guards the bound needs (`Math.max(0, …)` under
  the root, then clamping the result into the bucket) — correct.
- Default-page bit-identity holds (sea-relative ramp degenerates to the 0.3.3 ramp at sea 0;
  both renderers and the probe all read `Params.sea`).
- The CPU recolour defect in §1.2 item 1 was confirmed against `js/ui.js` sources: nothing on
  the level path sets `dirty`.

## 2. Plan amendments applied

### 2.1 0.4.0 — resolution story, now one crisp form

The 0.4.0 plan already said it (one baked pack, loader resamples onto the sim's grid) but also
hedged elsewhere — the default-resolution bullet (§3) and the `--deg 0.25` line in the order
(§9) both pointed at a nebulous "L8 question". The two force readings were reconciled to the
fixed-base form: the pack resolution is bake-side (`--deg`), the loader resamples to whatever
sim level the world is at (that is the whole "downscale to target level at load" the 0.4.0 draft
asked for), and the order's `--deg 0.25` mention now reads "after the 0.4.5 scoring question".

### 2.2 0.4.0 — change-resolution request added for the sim (§9a)

The review asked for live simulation-resolution change, which fits 0.4.0's "scale real data to
target resolution" theme first. It is added as a named out-of-scope section (§9a), because its
core is a sim property the Earth map must not silently contradict: **`level` is the column
grid's geometry, so a mid-sim level change is a world rebuild, not a Params knob.** The honest
re-use path is recorded for when it lands (the pack is a grid-independent raster, `Earth.apply`'s
resample is exactly what a finer/coarser re-seed would call), and the request is pointed at 0.6.0.

### 2.3 0.5.0 — displacement floor, and the no-mirror invariant

- §8 sets Displacement 1–40 (was 0–40): below 1× the terrain compresses while the shell holds
  `R + exag·sea`, land and shell cross, and at 0 the terrain collapses into the shell — a
  degenerate, not a view. The floor is documented as deliberate and carried into acceptance 4
  and the smoke (`disp 1` baseline instead of `disp 0`).
- §2 gains the invariant the other single-choice settled: the 3D consumes only the sim's own
  segment-final `z` (GPU `cellF` bind or CPU per-frame `cellZ`) — never a cached or re-sampled
  height — which is why the 2048×1024 texture for every k makes a resolution change cost zero
  3D work. Cross-linked to §12.
- The intro now notes the 0.3.5 control change: the 3D reads only the passive `Params.sea`, so
  "two sliders, last-active enable" needs no 3D work.

## 3. Tracked implementation items — done

1. Drop the checkbox and the `sea-volume` element; last active enables; other slider greys.
   **Done** — the greying is an `off` class on the label, not `disabled`: a disabled control
   would swallow the very click that re-arms its mode, so the inactive slider stays
   interactive and dimmed (pinned as a note in plan §4).
2. Level path writes `Params.sea` and sets `dirty = true` explicitly (the §1.2 bug).
   **Done** — `applySeaLevel` in `ui.js`; the volume path's `solveWater` sets `dirty` too.
3. Remove the mode from the capture header and the `?seamode` pre-fill; readouts become
   `+1.2 km` / `1.50× · +0.4 km` per the active slider. **Done** — `Params.seaVolume` is
   gone from `params.js` as well; no `seamode` token survives anywhere. The clamps carry
   the named readouts the plan promised (`dry` / `flooded`).
4. Tests to update: `tests/gui.js` (checkbox/disabled-flip replaced by last-active-enable; header
   only when non-default; pre-fill without `seamode`); `tests/water.js` is unaffected.
   **Done** — `tests/gui.js` gained the item-10 section (enable rule, recolour, deferred
   solve, pre-fill tie, header, probe follows `Params.sea`, the dry clamp) and `water.js`
   in its module list; `tests/water.js` additionally gained the plan §5 cases it did not
   yet have (bucket-edge round trip to 1e-9, the `N·w²/8` intra-bucket bound, the
   empty-bucket linear branch).
5. `webgpu-smoke.html` runs the z layer at a non-default sea on both engines; the volume solve's
   CPU-vs-GPU `L` at |ΔL| ≤ 60 m on the same L5 world. **Done** — the smoke page loads
   `js/water.js`, runs the z layer at −2.5 km and +1.2 km against the parity thresholds,
   and compares the solve on the CPU's `z` vs the GPU mirror's `z` at × 1 and × 1.5.

Nothing here changes the sim or the default rendering; the plan edits are in place.

## 4. Closeout

The deferred items above landed together with the plan brought to its final form:
`0.3.5-plan-water-level.md` §3 now describes the shipped architecture — one JS solver
(`js/water.js`) for both engines, reading `state.z` (the GPU engine's existing mirror, so
no new readback), with the device-side histogram kept as the documented upgrade path —
and §5/§6 match the tests and measurements that actually shipped (0.25 / 0.37 / 1.07 ms
at L5/L6/L7 on the sandbox). Verified: the 27-test short profile green, `tests/water.js`
and the new `tests/gui.js` section passing, no `sea-volume`/`seamode`/`Params.seaVolume`
reference left in the tree, and the default page bit-identical (sea 0, level mode).
