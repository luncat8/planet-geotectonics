1. The long play run: the checkpoint path is confirmed fixed on hardware.

   This was the third of the three captures 0.3-3-report.txt asked for, and it is the
   one that closes the getMappedRange story: the old defect died at a fixed point in
   time - a full sync followed by an event cycle, which the 20 Myr checkpoint is - and
   this run passes t = 20 Myr and keeps going to 268.2 and 328.6 Myr, i.e. thirteen and
   sixteen checkpoint cycles, with the event line still printing and the loop still
   playing (122-126 steps/s). No uncaught error, no stuck sim. frame 5.6 ms and p95 =
   max = 5.6-5.7 ms at 180 Hz, identical to the previous capture: the round trip did not
   get worse with world age, which is the distribution claim Phase II made.

   The event line itself moved a little and says where: 29.6 ms = dl 25.9 [wait 24.3]
   + cyc 3.2 + up 0.5, against 28.5 = dl 26.2 [wait 25.5] + cyc 2.0 + up 0.3 at t = 2
   Myr on the same rig. `wait` is still ~82% of the round trip, so the Phase IV reading
   (the drain, once per step) stands; but `cyc` went 2.0 -> 3.2 ms, and that is
   Events.cycle on a 328 Myr world (more plates, more ledger rows) rather than on the
   boot world the headless rig measured (2.09 ms). Phase IV's one-drain-per-rAF will not
   touch cyc, so the event total's floor at late epochs is ~3 ms of CPU cycle plus
   whatever drain survives - worth carrying into Phase IV's acceptance text.

   Four captures, two of them at t > 268 Myr with splits and sutures long past, and the
   K11 passes are 40-41% of the timestamped kernel total every time. Nothing on the
   device reads their output (only the CPU mirror does, at 6 Hz), so Phase III stays
   the next move and its expected win is now known to hold across the whole run, not
   just its start.

   Two reading traps in these tables, both about the kernel row's *contents* varying:
   the file:// row carries `resolve` and `thinning` (below the 0.05 ms floor in the
   http window) and drops `loserCount`, and the bench's kernel line in the same paste
   (winners 1.82 loserRank 1.05 diagC 0.59 diagA 0.31 ...) is an EMA over whichever
   configs had just run, so it must not be compared per-kernel against a play strip.
   This is the same variability the owner's second TODO is about: a strip whose rows
   and row lengths change at 2 Hz moves the page under it.

   One open question, cosmetic and unfixed: the file:// strip is playing at 126 steps/s
   - an event round trip completes every ~79 ms - yet its copy has no events row, while
   the http tab's does. The copy carries whatever the last 2 Hz update saw, so a copy
   taken between a round trip's completion and the next update can miss it; that is the
   only reading that fits, and it cannot be settled from a paste. With the reserved
   strip the row set is positional (throughput, distribution, events, checkpoint,
   kernels), so a future paste says which slots were empty instead of which rows the
   copy happened to catch.

   The paste header says `steps=1,5` and this is the third capture in a row without the
   20-step rows, which 0.3-3-report.txt attributed to the operator editing the field.
   The code says otherwise: bench.html parsed the steps field with
   `parseList(stepsIn, 1, 16)` while its own input defaults to `1,5,20` - so the auto-run
   on load, and any run with the defaults, silently filtered the 20 out before the first
   config was built. Three captures missed a row of the matrix because the measurement
   tool quietly measured less than the page said it was measuring. Fixed: the bound is
   `STEPS_MAX = 20` (index.html's Steps/frame select tops out there, so the bench has to
   reach it), and anything dropped from either field is now named - `BENCH ignored:
   steps 99 (outside 1-20)` on the console, in the status line and in the copy - so a
   config the page will not run can no longer look like one it did. tests/gui.js pins
   both halves: the bench's accepted ranges must cover every option the app offers, and
   the bench's own default field must survive its own filter.

   The four rows that are here repeat the previous bench within ~5% (L5 1: 9.650 vs
   8.520/8.800 iso; L6 5: 19.641 vs 19.799/19.829), so the matrix is stable and only the
   missing column is news. L6 5's smooth med 198.7 ms with 0/48 hitches is the saturated-
   queue signature again: at 5 steps/frame on L6 one rAF waits out ~200 ms of device work.
