The number this capture was taken for: **`dl 26.2 [wait 25.5]`**. Of the event
round trip's 28.5 ms, 25.5 ms is the device finishing work that was already
submitted before the cycle could read its mirror; the seven `mapAsync` round trips
plus the whole JS unpack are ~0.7 ms, and `cyc 2.0 + up 0.3` is the CPU side the
headless rig measured exactly (2.09 + 0.35). Consequences, all now in 0.3-plan.md:

  - one combined staging buffer and one map instead of seven is worth <= 0.7 ms.
    Not the next move.
  - Phase II's "<= 10 ms event total" target cannot be met by anything that stays
    a transfer: the drain has to stop happening once per step, which is Phase IV
    (n steps in one encoder, one submit, one drain per rAF).
  - Phase III keeps its place ahead of Phase IV: diagA 0.85 + diagC 1.46 = 2.31 ms
    of the 5.66 ms top-10 total (~41%; ~40% in the first capture, so the share is
    stable even though every kernel got faster), and nothing on the device reads
    them.

webgpu-smoke.html: 18 failures, and every one of them now has a name.

1. `[FAIL] meanSpeed drift > 20%` — defect D1, and the discriminator the previous
   session added is what makes it a measurement instead of a hypothesis:

	[parity] frame 5 dt 0.1 · n cpu=10242 gpu=10242 · plates cpu=16 gpu=16
	         · owner mismatch 0/10242 · |dz| max 139.0 m
	[parity] meanSpeed cpu=4.022 gpu=4.947 · maxSpeed cpu=11.449 gpu=13.026
	[parity] omega relaxation: mean |omega|/|omegaTarget| cpu 0.837 gpu 0.973 over 16 plates
	         · p1 cpu 0.943 gpu 0.991 · p2 cpu 0.691 gpu 0.966
	         · p3 cpu 0.871 gpu 0.828 · p4 cpu 0.863 gpu 1.167
	[parity] omega: worst |dR*w| plate 14 = 2.053 cm/yr
	         · cpu from relaxed omega 4.022/11.449
	         · cpu from target omega  5.040/13.052
	         · gpu                    4.947/13.026

   Read: the device's omega sits on the unrelaxed least-squares fit (mean ratio
   0.973, i.e. |omega| ~= |omegaTarget|), the CPU's lags it (0.837), and one plate
   on the device is *above* its own target (p4 1.167) which a relaxation with
   alpha = 0.2 can only do by inheriting a larger omega from the frame before.
   The speeds follow the same split: gpu 4.947/13.026 against cpu-from-target
   5.040/13.052 (1.9% mean, 0.2% max) and cpu-from-relaxed 4.022/11.449. So the
   world the device builds is the world the *fit* describes, not the world the
   relaxation describes — while `wgsl-plates.js reduceB` is line-for-line
   `js/plates.js reduce`, tau_omega is 0.5 in both generated sources, and dt is
   0.1 in both. Code reading has nothing left to give, so this session made the
   device report instead (0.3-plan.md I7):

     - `reduceB` leaves one witness per plate in the reduce scratch,
       `RED[RED_RELAX + p] = |omega_stored - (omega_prev + (fit - omega_prev)*alpha)|`,
       cleared every frame by `zeroFrame`;
     - `diagB` folds it into `DIAG[D_RELAXERR]` and reports the dt and alpha the
       same frame ran with (`D_DT`, `D_ALPHA`);
     - `pull` mirrors them to `state.gpuDt` / `gpuAlpha` / `gpuRelaxErr`, and the
       smoke prints a `device K10:` line and fails with four distinct messages:
       the device ran a dt the JS did not upload / the device's alpha is not
       `min(1, dt/tau_omega)` / the stored omega is not the relaxed omega / the
       device carries the fit while all three of those say the relaxation ran.

   Whatever the next capture says, D1 stops being a theory: those four branches
   are the only ones left, and each names a different file.

2. 16 x `[FAIL] pixel parity compared nothing on layer X (mean NaN)` and
   `[FAIL] webgpu/page errors captured` (32 errors). The errors named themselves
   this time, which was the point of Phase I5:

	webgpu uncaptured: [Texture "D3DImageBacking_D3DSharedImage_WebGPUSwapBufferProvider_Pid:17956"]
	  usage (TextureUsage::(TextureBinding|RenderAttachment)) doesn't include TextureUsage::CopySrc.
	   - While validating source [Texture "..."] usage.
	   - While finishing [CommandEncoder (unlabeled)].
	webgpu uncaptured: [Invalid CommandBuffer] is invalid due to a previous error.
	   - While calling [Queue].Submit([[Invalid CommandBuffer]])

   Two per layer, 16 layers. The Phase I4 "ask for COPY_SRC on the canvas" fix
   does not work on a real swapchain: Chrome/D3D backs a presented canvas with a
   shared image whose usage the swapchain chooses, so `configure({ usage })` does
   not make `getCurrentTexture()` a legal copy source (a software adapter honours
   it, which is why the headless rig never showed this). The copy died, the
   command buffer was rejected, the staging buffer kept its zeros — and the
   comparison printed `mean|d| NaN max|d| 0`, a line that cannot be interpreted:
   `max|d| 0` says every difference compared false while `mean NaN` says the
   quotient was 0/0 or had a NaN summand, and with two byte arrays neither is
   reachable from the code as written.
   Fixed both ways: `GpuRenderer.init(state, { readback: true })` now renders into
   its own RENDER_ATTACHMENT|COPY_SRC texture, copies that into a reused staging
   buffer (`readPixels()`) and blits it to the canvas with one nearest-sampled
   fullscreen triangle, so the compared pixels and the visible map are the same
   bytes and the canvas texture is never a copy source. And phase 4 now reports
   the sample count per layer, divides by the samples actually compared, and fails
   with all three sizes (canvas / readback / CPU reference) when the comparison
   cannot be set up — a gate on a rig visit has to explain itself.
