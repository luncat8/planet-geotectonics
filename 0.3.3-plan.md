# 0.3.3 — Live adjustment plan: temperature, friction, erosion, relief ramp

Implements `0.3.3-draft-adj.md`: adjust global settings in this sim without
performance loss — friction, mantle temperature (Cooling checkbox + Mantle Tm
slider, the slider following the sim at 2 Hz while cooling), erosion speed (the
default is too fast and too independent of mountain height: it should prevent
30 km peaks without eating 2–3 km relief), and an elevation color-range slider.
The controls ride the Adjust group built in `0.3.2-tweak-ui.md`; every one
applies live on both engines, mid-play, with no restart.

## 0. What can be adjusted live, and what it costs

Measured basis: how a parameter reaches the frame today.

1. **JS-side scalars — free on both engines.** The mantle bookkeeping is CPU JS
   by design: `Mantle.update` (CPU engine) and `GpuSim.fillFrame` (GPU engine)
   compute `state.Tm` and the mantle speed per frame before anything runs on the
   device, and the device receives them through the frameIn block. Anything
   those functions read can change every frame at zero cost. Temperature lives
   entirely here.
2. **frameIn promotion — free, small layout bump.** The WGSL bakes parameters as
   `P_*` consts (`wgsl-common.js params()`), but the two kernels the sliders
   need already bind `frameIn`: `forces` (reads `P_EA`) and `erode` (reads
   `P_KERO`). A baked const they read can become a frameIn float at identical
   cost. Blocks use 74 of `finStride` 80 floats (32-byte alignment) — 6 spare,
   enough for both sliders with 4 spare left. No new bindings, no pipeline
   recompiles, and when the slider sits at its default the value is
   bit-identical to the baked path (multiplying by 1.0 is exact in f32/f64).
   Rule: promote only what a slider moves; the long tail stays baked (a const is
   cheaper than a uniform load and the WGSL stays readable).
3. **Renderer inputs — free.** The GPU draw already writes a per-draw uniform
   (`struct U { layer: u32, viewQ: vec4<f32> }`); one more f32 rides along. The
   CPU renderer reads a module global inside `draw`. Pure render cost, none of
   it per-sim-frame.
4. **Not cheap — stays out.** Params baked into kernels that do not bind
   frameIn (contact, scan, plates reduce) would need a new binding or a pipeline
   rebuild per change; world-structural params (level, plateCap, radius) are
   startup-only by nature. They stay where they are.

The GPU kernels change in exactly two places (forces, erode) plus the draw
shader's uniform struct, so closing this plan requires the rig: parity ensemble,
smoke, and the full profile (§3's recalibration demands it anyway).

## 1. Temperature — Cooling checkbox + Mantle Tm slider (free)

Today: `state.Tm0` (map start `Tm0`, hot start `TmHot`) is checkpointed;
`Tm(t) = Tfloor + (Tm0 − Tfloor)·exp(−t/tauCool)`; every frame recomputes
`state.Tm` from it and the mantle runs on `speed = U0·Tm^2.5`, plume heat
`str·Tm`, and `cD(Tm) = exp(Ea(1/Tm − 1))` damps the driving forces.

- **Cooling checkbox**, default checked = today's behavior. Unchecked, `state.Tm`
  is pinned: `Mantle.update` and `fillFrame` use the stored Tm instead of
  recomputing from t. Nothing else reads t for temperature, so this is one
  branch in each of the two functions.
- **Mantle Tm slider**, range `Tfloor..2.0`, step 0.01, applies on `input`:
  - cooling on: re-derive the checkpointed baseline so the world keeps cooling
    on from the new value — `Tm0' = Tfloor + (v − Tfloor)·exp(t/tauCool)`. No
    schema change, the decay continues naturally from this moment;
  - cooling off: `state.Tm = v` directly.
- **The slider follows the sim at 2 Hz** (the `Perf.TEXT_MS` tick) while cooling
  is on, and never while the user is editing it (`document.activeElement`
  guard) — the draft's "if (enabled Cooling) update slider 2hz".
- GPU: zero device changes — the value reaches the kernels through the existing
  `fTM()` frameIn slot.
- Checkpoint: add `cooling` to SCALARS and bump **VERSION 1 → 2**; a v1 blob is
  rejected by the existing version check (no legacy support).
- With defaults (cooling on, slider at the boot value, never touched) `Tm0` is
  untouched and the release profile stays bit-identical.

## 2. Friction — the asthenosphere damping exponent (frameIn promotion)

"Friction" is defined as the temperature damping of the driving forces — the
physical slider the engine already has: `Plates.forces` computes
`invCD = exp(−Ea·(1/Tm − 1))` and scales ridge push, slab pull and collision by
it. `Ea` (default 3) is the coupling's friction: 0 leaves the forces undamped
(a cold mantle drives as hard as a warm one); larger damps the cooling world
into a stagnant lid sooner.

- Slider **Friction ×**, range 0..3, step 0.05, default 1.0; effective
  `EaEff = Ea·friction`, multiplied in the same order on both sides
  (`P_EA * fFriction() * (1.0/fTM() − 1.0)`) so default = bit-identical.
- CPU: one extra multiply in `Plates.forces` (the single `invCD` computation).
  `dragFit` is drag-only and untouched.
- GPU: the `forces` kernel promotes one frameIn slot (`fFriction()`); `reduceA`
  / `reduceB` / contact unchanged.
- Alternative considered and rejected: scaling `tauOmega` (plate sluggishness).
  The ω relaxation is pinned by the parity harness and the dt-insensitivity
  argument; the damping exponent touches one expression and couples correctly
  with the temperature control above (one knob decides how hard cooling bites).

## 3. Erosion — a height-dependent law + speed slider (frameIn promotion, recalibration)

Today (`Surface.route`, WGSL `erode`): `want = kEro·z·(1 + 2·slope/slopeRef)·dt`
— linear in elevation, so low relief erodes at a proportional rate and the
calibration eats 2–3 km shields fast while doing comparatively little about a
30 km peak. The draft is right, and the fix is a quadratic knee — polynomial
only, so the f32 WGSL port is exact (no pow/exp enters the kernel):

```
q = z / zKnee                        (zKnee = 6500 m, a const, the ramp's own reference)
want = kEro · eroScale · z · q · q · (1 + 2·slope/slopeRef) · dt
```

- Continuous with the old law at the knee (q = 1); below it the rate falls
  quadratically (2.5 km → ~0.15× today), above it rises (13 km → 4×, 30 km-scale
  peaks → ~21×). Peaks are prevented; 2–3 km terrain survives. The knee is a
  calibrated const `P_ZKNEE`, not a user control; the user control is speed.
- Slider **Erosion ×** (`eroScale`), range 0..3, step 0.05, default 1.0.
- CPU: two extra multiplies in `Surface.route`; sediment routing, deposition and
  the placer liberation formula are untouched — only the intake changes.
- GPU: the `erode` kernel promotes one frameIn slot (`fEroScale()`); `routeOut`
  / `stay` / `deposit` untouched.
- dt-insensitivity: the q² factor is dt-independent, as the old z factor was.
- **The default change is a calibration change.** Phase G calibrated `kEro`
  against the linear law, so the release statistics move: expect higher sustained
  relief, slower erosion of low shields, and knock-on shifts in sediment-driven
  potentials (basin, placer). This is allowed only with a re-proof, per the
  0.2/0.3 convention: the owner-rig full test re-run and its baseline re-committed
  (longrun 1500 Myr end-state, the dt 0.01 300-Myr cross-check, the four
  histories), the 4.5 Gyr release profile re-run, the parity ensemble green on
  the rig, and one iso bench confirming ms/step is unmoved (two multiplies).
  Statistics drift without that re-proof is a plan failure, not a tunable.

## 4. Elevation color range — the relief ramp (renderer only)

Both renderers hard-code the ±6500 m ramp (`render.js` draw's z branch;
`render-gpu.js` SHADER `1.0 + z / 6500.0`).

- Slider **Relief range**, 2..20 km, step 0.5, default 6.5 km. The value is the
  ramp cap for land and, symmetrically, the deep-water floor:
  `shallow = max(0, 1 + z / (−range·1000))`, `high = min(1, z / (range·1000))`.
- CPU: `Renderer.zRange` module global, read in `draw`; changing it sets
  `dirty` (a recolour, not a view move).
- GPU: extend the draw uniform to
  `struct U { layer: u32, viewQ: vec4<f32>, zRange: f32 }` (padding keeps the
  16-byte alignment), written by the same per-draw uniform write as the layer
  id; the shader divides by it. The shader module is built once at init with
  the new struct — a uniform, so no pipeline rebuild when the slider moves.
- While playing, the next frame's draw picks the new range up; paused, the
  dirty redraw + drained-queue present shows it.

## 5. UI placement, capture headers, URL pre-fill

- All four controls live in the **Adjust** group, after Engine: `Cooling`
  checkbox, `Mantle Tm` range, `Friction ×` range, `Erosion ×` range,
  `Relief range` range — styled like the existing checkboxes (accent color,
  compact), no new group.
- `perfReport` records the adjustments so a capture is reproducible: one line
  `adj Tm 1.20 cooling off · friction 1.4x · erosion 0.6x · relief 9.0 km`,
  printed only when something differs from the default (the copy header keeps
  its shape otherwise — the same policy the `view gate:` line uses).
- URL pre-fill mirrors `?level/?seed/?dt/?steps/?cadence`:
  `?tm=1.4&cool=0&fric=1.5&ero=0.5&relief=9`, so a capture request can name its
  adjustments instead of describing clicks.
- `bench.html` unchanged: the bench measures the default kernel path, and a
  slider cannot change what it measures.

## 7. Order and acceptance

Order: temperature (JS only) → relief ramp (renderer only) → friction (first
frameIn promotion, no default change) → erosion (second promotion plus the
recalibration, carries the full-profile re-proof).

Acceptance:

1. Every control applies live mid-play on both engines with no restart and no
   measurable stutter: ms/step within noise of the pre-change bench at L5 and L6.
2. Defaults are bit-identical for temperature, friction and relief (frame-2
   clone test + ensemble); erosion's new default is proven by the re-committed
   full-test baseline, the dt 0.01 cross-check and a fresh rig ensemble.
3. Checkpoint VERSION 2 round-trips `cooling` and the adjustments; a v1 blob is
   rejected with the version message.
4. The capture header names the adjustments when non-default, and `?`-prefill
   reproduces a capture's settings from its log line alone.
5. The long tail stays untouched: no kernel outside `forces`/`erode`/the draw
   shader changes, no new bindings, `finStride` and the 32-byte alignment hold.
