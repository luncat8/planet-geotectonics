## 2. What was reproduced

### 2.1 The ledger gate was stricter than the design

The one gained cell is not a mask bug. `Resolution.ledger` absorbs a rim record into the target
cell its direction names when the inherited mask does not cover that cell (`moved 1/1`). The
union of source masks adds nothing on this fixture (`gainUnion 0`). The old gate asserted the
absorption never happens, which contradicts the code comment that justifies it.

**Fix:** the report now splits the gain into `gainUnion` (the mask's own growth) and `absorbed`
(rim records), with `coverageGain = gainUnion + absorbed`. The test asserts that identity, and
that the union adds nothing on this fixture. Gate changed, behaviour unchanged.

### 2.2 The plan's family-volume rule cannot hold as written

`0.7.0-plan-live-resolution.md` §3.2 gives each target cell `h_t = A0ref_s·h_s / (share_s·A0ref_t)`.
For L5→L6 `A0ref_s/A0ref_t = 4`, so a source column feeding two target cells gets `2h` in each and
one feeding four gets `h`. The thickness of a split child then depends on how many cell centres
happened to fall in its footprint: a ±50 % stripe across the map. The implementation's author
saw this and used an area-weighted mean over contributors instead (`js/resolution.js`,
`transferColumns`). That is the physically right call, and the plan's §3.2 is corrected to it.

The price is that the mean does not conserve volume exactly. It is booked to the ledger's
`regrid*` terms and reported. Measured on the short profile:

| Case | Family volume residual (fel) | Note |
| --- | --- | --- |
| Fresh L5 world → L6 | 0.50 % | every child is one of the parent thicknesses (no invented value) |
| Fresh L6 world → L5 (round trip of a uniform world) | 0.47 % | |
| Stepped L5 (50 steps) → L6 | 3.90 % | the transfer's own number, booked to `regrid`; 100 % of children on an exact parent value |
| That L6 world → L5 | 0.28 % | a transferred world, not a stepped one |
| Six alternating changes from the stepped world | 4.93 % cumulative | worst single 3.90 %; ledger identity closes |

The ledger identity closes exactly because the residual is booked; the crust volume is not
conserved in the physical sense. See §4 for the decision this leaves open.

### 2.3 Inventory classification

`gaps`, `maxClimb`, `finite`, `rigidError` and `quatError` are written by `Columns.raster`,
`Columns.bin` and `Diag.check`, which all run again on the target. They were classified as
`world` (copied). The copy is overwritten, so no number is wrong, but the classification
contradicts the plan's §2 table, which puts `gaps` in the re-derived coverage frame.

### 2.4 An overstated assertion

The PASS line said the transfer "conserves every family". It books a residual; the line now says
so.

### 3.2 The page: slice 3, CPU engine

The Resolution select used to rebuild the world from scratch at any level. On a running CPU
world it now **offers** the change: the select shows the new level, a bar offers
**Keep world at L6** (the conservative transfer) or **Fresh world at L6** (the old rebuild), and
nothing moves until one of them is clicked. Fresh worlds (frame 0), the GPU engine and a live
Reconstruct scrub keep the rebuild path, as before.

Keep world:

1. builds the target grid and `Resolution.transfer(state, next)` and re-lays the ledger
   (`Resolution.ledger`) **on the side**; any throw shows `Keep world failed (…); the L5 world
   is unchanged` and writes nothing;
2. commits: cancels a running campaign (`cancelCampaign`), swaps `grid`/`state`, rebinds the
   renderer, the deposit cache, the 3D height lookup (`rebootV3d`), the water histogram, the
   ledger overlay and rows, and the perf strip.

Pins and ledger ids are kept. The old `discardCampaignForRebuild` also dropped pins and the
ledger view; it is now split so a rebuild keeps dropping them and a keep does not.

Tests: `tests/gui.js` drives the offer, Fresh world (the old rebuild assertions), a failing
transfer on a stepped L5 world (the old world, its clock and the bar stay; the failed offer is
withdrawn), a successful keep (clock carried, the sim steps on the new grid), and the
same-level no-op. The keep block runs last in the file because a second `loadPage` replaces the
page globals (`GpuSim`, `Resolution`) that the earlier sections drive.

Two existing GUI sections changed intent, not assertions: the view-outlives-rebuild check and
the heightfield-rebuild check now click **Fresh world** explicitly, because they test a rebuild.

## 4. Open decisions (not decided here)

1. **Volume residual.** Options:
   - (a) keep the booked residual (current): the field stays per-parent, the ledger closes, the
     crust volume is not conserved (3.9 % per L5↔L6 change on a stepped world, 4.9 % after six);
   - (b) a global conservative fixer, one scale per family, so volume is exact; every thickness
     moves by the residual (~0.5-4 %), so no child keeps an exact parent value;
   - (c) an overlap-weighted remap (sub-sampled footprints), which should conserve locally and
     is the most work. Its cost has to be measured before it is chosen.
   The plan's §4.2 "no new crust" and §9 "no visual filter on transfer" pull against each other
   here; this is a decision for the owner, not a bug to patch silently.
2. **GPU device path (slice 4).** Needs the owner rig (arena re-init at the new level, upload of
   the transferred state, the L6/L7 gates). No sandbox run establishes a device claim.
3. **Drift.** Six alternating changes drift the crust by 4.9 % (§2.2). The test's name says
   "do not compound" and its gate is `< 6 %`. That gate is a budget, not a property.
