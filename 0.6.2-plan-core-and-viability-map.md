# 0.6.2 — Stratigraphic core and the optional viable-deposit map

The third increment of the deposit prospector (`0.6.x-plan-deposit-prospector.md`). It adds the
**core** a hole brings up and, as an explicit opt-in, a regional campaign that surveys the planet
with the checked instruments and maps deposits that survive the 0.6.1 viability screen. This
broad view is a convenience for a deliberate regional question, not the primary way to prospect:
the normal workflow remains selecting instruments and clicking one cell. Nothing scans the planet
on load, on hover, or as a side effect of a local survey.

Prerequisites: 0.6.0 (instruments, pinned report and ledger) and 0.6.1 (the numeric record).
Nothing here changes a record, a parameter of the class table, or the checkpoint.

## 1. The core

`js/core.js` turns a column and a hole depth into a lithological log. It reads only state the sim
already carries — `hSed`, `hFel`, `hMaf`, `wet`, `z`, `Params.sea`, the potentials, the catalogue's
records — and it is a pure function of `(state, cell, depth, seed)` under the S1/S2 quantization
rules:

- **Inputs are quantized**: thicknesses enter on 50 m buckets, bed boundaries come out on 1 m,
  ore intervals on 1 m, grades from the record (already 2 s.f.). Two calls at the same state print
  the same log; a call after 10 Myr differs only where the column itself moved a bucket.
- **Identity**: bed thickness and lithology hashes are keyed on the column *anchor*
  (`body`-derived key, as in 0.6.1), not on the cell, so a plate carrying a borehole site across a
  cell does not re-roll its stratigraphy. The cell index only picks *which* hole was drilled.

### 1.1 The section

`Core.section(state, cell, depth)` returns layers top→bottom, contiguous and metre-based, from the
datum (the surface; the seafloor when `wet`, with the water column as layer 0):

| # | layer | rule |
|---|---|---|
| 0 | `seawater` | `wet` only: `max(0, round((Params.sea − z)/10)·10)` m; the datum is then the seafloor |
| 1 | sediment beds | `hSed` split into `n = clamp(round(hSed/120), 1, 12)` beds, thicknesses from the anchor hash, lithology by context — sand / silt / clay / marl / evaporite |
| 1a | `coal seam` | inside the sediment package when the cell holds a `basin.coal` record or `oBas ≥ 0.4` on land; 0.5–4 m, top from the hash |
| 1b | `gravel, pay streak` | when the cell holds a `placer` record, or `oPla ≥ 0.3` and a placer record one hop downhill; near the base of the package |
| 1c | `sandstone, U-bearing` | when the cell holds a `basin.uranium` record; a 1–10 m bed with a redox boundary |
| 2 | `granite / gneiss / greenstone` | while `hFel` remains; alteration adjectives from `oArc`/`oOro` (`sericite-altered`, `sheared`); `PORPHYRY STOCKWORK` or `QUARTZ LODE` intervals when a record body lies in the hole |
| 3 | `gabbro / basalt / peridotite` | while `hMaf` remains; `MASSIVE SULFIDE LENS` (vms), `sill, disseminated sulfide` (mafic), `BIF` (iron) when the record body lies in the hole |
| 4 | `mantle` | below `hSed + hFel + hMaf`: listed only if the hole is deeper than the crust, and the hole stops there |

Ore intervals carry `ore: true`, the record `id`, the principal grade, and are drawn from the
record's own `bodies[]` (top, bottom) — the core never invents an intersection the catalogue does
not have, and the catalogue never places a body below `hSed + hFel + hMaf` (its emplacement and
footprint rules keep it inside the crust; the consistency test in §4 holds the pair together).

`Core.text(section)` prints a fixed-width log:

```
hole 4,812 · L5 · 43.1°N 12.7°E · continental shelf · water 110 m · sediment 240 m · depth 5,000 m
    0 -    110 m  seawater
  110 -    230 m  sediment   sand, quartz, cross-bedded
  230 -    350 m  sediment   silt with plant debris; coal seam 0.8 m at 300 m
  350 -    470 m  granite    biotite granite, sericite-altered
  470 -    710 m  granite    PORPHYRY STOCKWORK  Cu 0.38 % Mo 0.009 %   #7a04c3d1
  710 -  2,900 m  gabbro     MASSIVE SULFIDE LENS  Cu 1.2 % Zn 3.1 %     #b7c1e088
2,900 -  5,000 m  peridotite serpentinised
```

`Core.json(section)` writes `{ format: 'pgt-core', version: 1, cell, epoch, depth, datum, layers,
intersections }` — one format, no parallel schema.

### 1.2 UI

The local Prospect report grows a core block: `Hole depth` select (`500 m`, `2,000 m`, `5,000 m`,
`to basement`), the text above in the report, and `Export core` writing the JSON of the last hole.
The core is regenerated on click and on depth change — never per frame. Picking a marker can be a
shortcut after a user explicitly runs a regional campaign; it is not required for ordinary
single-cell exploration.

## 2. The opt-in regional campaign and viable map

The regional control is explicitly labelled `Survey all cells · build viable map`, so its scope is
clear before it starts. It is a secondary, deliberate tool; the app opens with no campaign running,
and every ordinary click continues to survey only the selected cell's instrument footprint. When
the user asks for a broad answer, the checked instrument set is applied to every cell, the ledger
fills, and the map shows what that set found and 0.6.1's screen kept. It is deliberately not
omniscient — a player without `d5k` gets a map of deep deposits they cannot see.

- `Instruments.campaign(state, catalogue, set, cursor)` walks cell indices in ascending order only
  after the user presses the regional control, calls the same `survey` logic with reporting
  suppressed, and writes the ledger. It is chunked: `CAMPAIGN_PER_FRAME = 2000` cells per frame
  at L5, scaled by `10242/grid.V` — bounded work per frame, progress line in the panel
  (`campaign 42 % · 4,310 cells · 118 found · 37 viable`), and the button toggles to `Cancel` while
  it runs. The catalogue build happens once at campaign start, never per chunk.
- The catalogue is rebuilt at campaign start (S6's snapshot); if `state.t` has advanced more than
  5 Myr since the last build the panel says `stale — press again`, and a second press is a fresh
  campaign.
- After the campaign: `Deposits.summary(state)` prints the planet's numbers, grouped by kind and
  commodity with the class table's own units:

```
viable deposits 37 · contained in the ground
  Cu 12.4 Mt   Mo 0.21 Mt   Au 402 t   Ag 3.1 kt   Zn 6.8 Mt   Pb 0.9 Mt
  Ni 1.2 Mt    PGE 44 t      U3O8 18 kt  K2O 21 Gt   coal 44 Gt   Fe 1.9 Gt
largest by contained metal
  #b7c1e088  vms      Cu 1.2 Mt Zn 4.4 Mt   480 Mt       arc belt, 62 Ma
  #3f2a91c4  arc      Cu 260 kt Mo 6.8 kt   62 Mt        porphyry, 312 Ma
  …
epoch 1500.0 Myr · surveyed 10,242 cells · instruments d500,geo,mag
```

- **Markers**: filled diamonds for viable records, hollow for records above `depositMin` that
  failed the screen, drawn through `MapView.project` on a new `#markers` overlay in 0.6.2. This
  layer does not exist in 0.6.0; it appears only after an explicit regional campaign. A `Kinds`
  select filters the overlay and summary (`all` by default), and the drawn set is bounded.
- **Exports**: `Export deposits` writes `Deposits.json(state, { viableOnly })` (the v2 format of
  0.6.1; no third schema) and the summary block is the same object's `totals`.

Two deliberate choices:

1. **The local click loop stays primary.** Most questions concern one pointed-to cell; the campaign
   is an explicit broad sweep for players who need it, never a default, pre-check or hidden cost of
   local reports.
2. **The campaign uses the player's instruments.** The map is a survey, not an oracle: nothing
   appears that no checked instrument could find, and every marker inherits the confidence its
   discovery reached.

## 3. Cost

- Core: O(beds + bodies) ≈ tens of operations; text formatting allocates once per click.
- Campaign: `CAMPAIGN_PER_FRAME` cells × (union footprint ≤ 37 cells + hashes) — measured target
  ≤ 1.5 ms per frame at L5 on this sandbox, so a 10,242-cell planet finishes in ~6 frames of real
  work; at L7 the chunk scales to 2,000 × 10242/163842 ≈ 125 cells/frame and a full campaign is
  ~1,300 frames (minutes of play, or a second button press per region if the owner later wants
  regions). The measured numbers go into the calibration table in `0.6.1` §10 when the increment
  lands.
- The new overlay redraws only when the frame/map, view, filter or campaign result changes; it adds no per-frame scan and is absent until a campaign result exists.

## 4. Tests

`tests/core.js` (new):

1. **Bookkeeping** — layers are contiguous, start at the datum, end at the hole depth or the crust
   bottom, all thicknesses ≥ 0, the sum equals the depth (or the crust thickness when the hole
   bottoms out), and the water layer exists exactly when `wet`.
2. **One record, two holes** — a synthetic column carrying an `arc` record with bodies at 470–710 m
   marks the interval in the 5 km log and not in the 500 m log; the ore interval's `id` and grade
   equal the record's.
3. **The core does not contradict the catalogue** — over a 1500 Myr L5 run, every ore interval in
   every core is inside the corresponding record's `[top, bottom]` within one 50 m bucket, and
   every body inside the hole depth appears.
4. **Context beds** — `coal` only with a coal record, `gravel` only with a placer record (or the
   `oPla` + downhill test), `U-bearing` only with a uranium record; none of them on a cell whose
   context fails.
5. **Determinism** — two calls identical; identical after a checkpoint round trip; a body-carrying
   column that moves a cell keeps its bedding.
6. **Text and JSON** — the log's line count equals the layer count, the JSON parses, `version` is
   the literal, and a free-depth request (`to basement`) ends at the crust bottom.

`tests/instruments.js` (extended): the campaign's chunking (progress is monotone, the ledger after
N chunks equals a straight loop over the first N cells), determinism (same set ⇒ same ledger and
same summary), cancel leaves a valid partial ledger, and the campaign with an empty set refuses.

`tests/gui.js` (extended): `Survey all cells · build viable map` refuses with an empty instrument
set, runs only after an explicit click, completes in the stub's frame loop, prints the summary,
filters by `Kinds`, and `Export core`/`Export deposits` write their tags. `?inst=…&depkind=…`
prefill; the capture line gains campaign counts only after a campaign has run.

## 5. Order and acceptance

Order: `Core.section` + text (reads local records, no UI) → the pinned report's core block →
explicit `campaign` chunked over frames with the progress line → summary + markers + exports →
tests. Local click-to-survey remains available throughout and never waits for or starts a campaign.

Acceptance:

1. **Local first; regional only by request**: a fresh load performs no all-cell work; a one-cell
   click evaluates only its footprint. The labelled regional button applies the selected
   instruments to every cell only after an explicit click; with no instrument checked it refuses.
2. **Totals are exact**: the summary's contained metal equals an independent sum over
   `Deposits.viable(state)` filtered by the ledger, to the tonne (the test recomputes it from the
   records, not from the summary).
3. **Frame budget**: the campaign's per-frame work stays under 1.5 ms at L5 (measured, recorded),
   the catalogue build is not re-entered per chunk, and a running play frame keeps its ms/step.
4. **The core and the catalogue agree** (§4.3) over the whole 1500 Myr run.
5. **No engine work**: `git diff` for the increment touches no file under `js/gpu/`, no WGSL
   source, `js/render.js` beyond the added `MapView.project`, and leaves the parity harness green
   by construction; the short profile plus the ores/longrun histories are green on the owner rig,
   with the calibration table in `0.6.1` §10 filled from the release run.
6. **A capture restores choices without surprise work**: `?inst=…&depkind=…&core=5k` restores
   instrument selection, filter and hole depth, but never starts a campaign on page load. The user
   must explicitly start a regional sweep again.
