# 0.6.2 — Stratigraphic core and the optional viable-deposit map

The third increment of the deposit prospector (`0.6.x-plan-deposit-prospector.md`). It adds the
**core** a hole brings up and, as an explicit opt-in, a regional campaign that surveys the planet
with the checked instruments and maps deposits that survive the 0.6.1 viability screen. This
broad view is a convenience for a deliberate regional question, not the primary way to prospect:
the normal workflow remains selecting instruments and clicking one cell. Nothing scans the planet
on load, on hover, or as a side effect of a local survey.

Prerequisites: 0.6.0 (instruments, pinned report and ledger) and 0.6.1 (the numeric record).
Nothing here changes a record, a parameter of the class table, or the checkpoint.

## 1. The core

`js/core.js` turns a column and a hole depth into a lithological log. It reads only state the sim
already carries — `hSed`, `hFel`, `hMaf`, `z`, `Params.sea`, the potentials and local 0.6.1 records —
and it is a pure function of `(state, cell, depth, seed)` under the S1/S2 quantization rules. A hole
depth is measured from the local land surface or sea surface; water consumes drill depth. Deposit
body depths are below the seafloor, so wet-cell intersections are offset by the rounded water depth
when placed in the log.

- **Inputs are quantized**: crust thicknesses enter on 50 m buckets, water on 10 m, bed boundaries
  and ore intervals are integer metres, and grades come from the record (already 2 s.f.). Two calls
  at the same state print the same log; a call after 10 Myr differs only where the column itself
  moved a bucket.
- **Identity**: bed thickness and lithology hashes are keyed on the column *anchor*
  (`body`-derived key, as in 0.6.1), not on the cell, so a plate carrying a borehole site across a
  cell does not re-roll its stratigraphy. The cell index only picks *which* hole was drilled.

### 1.1 The section

`Core.section(state, cell, depth)` returns layers top→bottom, contiguous and metre-based, from the
local surface datum (land surface or sea surface):

| # | layer | rule |
|---|---|---|
| 0 | `seawater` | when `z < Params.sea`: `max(0, round((Params.sea − z)/10)·10)` m; it is the first interval and consumes hole depth |
| 1 | sediment beds | quantized `hSed` split into `n = clamp(round(hSed/120), 1, 12)` beds whose integer-metre thicknesses sum exactly to the package; lithology by context — sand / silt / clay / marl / evaporite |
| 1a | `coal seam` | split into the sediment package when a local `basin.coal` record exists, or `oBas ≥ 0.4` on land; 1–4 m, top from the anchor hash |
| 1b | `gravel, pay streak` | split near the base when a local `placer` record exists, or `oPla ≥ 0.3` and a placer record is one hop downhill; 1–3 m |
| 1c | `sandstone, U-bearing` | split into the package when a local `basin.uranium` record exists; 1–10 m, with the redox boundary named in its detail |
| 2 | `granite / gneiss / greenstone` | quantized `hFel`; alteration adjectives from `oArc`/`oOro` (`sericite-altered`, `sheared`); porphyry / quartz-lode intervals come only from record bodies intersected by the hole |
| 3 | `gabbro / basalt / peridotite` | quantized `hMaf`; VMS lens, disseminated sulfide sill and BIF labels come only from intersected record bodies |
| 4 | `mantle` | below the quantized crust bottom; a fixed-depth hole that passes the Moho logs mantle to its requested depth; `to basement` stops at the Moho |

Feature beds split their host interval; they never add overlapping thickness. Ore bodies are
*overlays* on the host layers: their top/bottom boundaries split a host interval and matching
segments carry `ore: true` plus an `oreRecords[]` entry for every intersecting body (the legacy
`id`/grade fields name the first overlay). This also preserves genuinely overlapping bodies
without inventing a second rock thickness. Each intersection is drawn only from its record's own
`bodies[]`; on wet cells add the rounded water-column depth when translating the record's
seafloor-relative interval into sea-surface-relative log coordinates.

`Core.text(section)` prints a fixed-width log:

```
hole 4,812 · L5 · 43.1°N 12.7°E · continental shelf · water 110 m · sediment 240 m · depth 5,000 m
    0 -    110 m  seawater
  110 -    230 m  sediment   sand, quartz, cross-bedded
  230 -    350 m  sediment   silt with plant debris; coal seam 0.8 m at 300 m
  350 -    470 m  granite    biotite granite, sericite-altered
  470 -    710 m  granite    PORPHYRY STOCKWORK  Cu 0.38 % Mo 0.009 %   #7a04c3d1
  710 -  2,900 m  gabbro     MASSIVE SULFIDE LENS  Cu 1.2 % Zn 3.1 %     #b7c1e088
2,900 -  5,000 m  peridotite serpentinised
```

`Core.json(section)` writes `{ format: 'pgt-core', version: 1, cell, epoch, depth, datum, layers,
intersections }` — one format, no parallel schema.

### 1.2 UI

The local Prospect report grows a core block: `Hole depth` select (`500 m`, `2,000 m`, `5,000 m`,
`to basement`), the text above in the report, and `Export core` writing the JSON of the last hole.
Numeric depth includes seawater; `to basement` ends at the quantized Moho and never adds a mantle
interval. A click regenerates the core even when no instrument is selected, but does not add survey
coverage in that case; a depth change regenerates only the last clicked hole. Neither action runs
per frame or builds the whole catalogue. Picking a marker can be a shortcut after a user explicitly
runs a regional campaign; it is not required for ordinary single-cell exploration.

## 2. The opt-in regional campaign and viable map

The regional control is explicitly labelled `Survey all cells · build viable map`, so its scope is
clear before it starts. It is a secondary, deliberate tool; the app opens with no campaign running,
and every ordinary click continues to survey only the selected cell's instrument footprint. When
the user asks for a broad answer, the checked instrument set is applied to every cell, the ledger
fills, and the map shows only what that set found, distinguishing records that pass 0.6.1's screen
from those that fail it. It is deliberately not omniscient — a player without `d5k` gets no marker
for a deep deposit they cannot see.

- `Instruments.startCampaign(state, catalogue, set, ledger)` creates a job; `campaignStep(job,
maxCells, maxMs)` walks cell indices in ascending order and runs the same eligibility, reach,
noise, confidence and ledger rules as a local survey, with report formatting omitted. `cancelCampaign`
leaves the valid partial ledger intact. The UI invokes bounded chunks only after the user presses
the regional control; empty instrument sets are refused. Each chunk is capped at 256 cells and
stops at a measured 1.25 ms budget checked every eight cells. Progress is monotone and reads
`campaign 42 % · 4,310 cells · 118 found · 37 viable`. The catalogue is built once at campaign
start and reused by every chunk.
- Campaigns use one coherent snapshot. Starting on the GPU pauses playback, drains the device and
reads the mirror once before building the catalogue; CPU campaigns pause playback before building.
Play and Step stay disabled while a job runs. The job stops if its state's frame or epoch changes,
so records from different snapshots can never be mixed. The catalogue and job retain the exact
simulation time as well as the rounded display epoch; a completed map is marked stale only after
the live world moves more than 5 Myr from that exact snapshot time. The first refresh press explains
`stale — press again`; the second starts a fresh, paused campaign.
- The map, summary and campaign export are filtered through the session ledger: a marker appears
only for a record the selected instruments (or an earlier local survey in this session) found.
The already-existing full `Deposits JSON` action remains a separate, explicit all-catalogue export.
The `Kinds` select filters markers, counts and top-ten lists but does not rerun the campaign.
- After the campaign: `Deposits.summary(state, { catalogue, ledger, kind })` prints the discovered
snapshot, with `contained` summing *viable* records in the ledger, not unmeasured records elsewhere
on the planet. It reports totals by metal/commodity in tonnes and the ten largest viable records
per kind (computed over the full filtered set, not only the catalogue's display-rank cache):

```
viable deposits 37 · contained in the ground
  Cu 12.4 Mt   Mo 0.21 Mt   Au 402 t   Ag 3.1 kt   Zn 6.8 Mt   Pb 0.9 Mt
  Ni 1.2 Mt    PGE 44 t      U3O8 18 kt  K2O 21 Gt   coal 44 Gt   Fe 1.9 Gt
largest by contained metal
  #b7c1e088  vms      Cu 1.2 Mt Zn 4.4 Mt   480 Mt       arc belt, 62 Ma
  #3f2a91c4  arc      Cu 260 kt Mo 6.8 kt   62 Mt        porphyry, 312 Ma
  …
epoch 1500.0 Myr · surveyed 10,242 cells · instruments d500,geo,mag
```

- **Markers**: filled diamonds for viable records, hollow for records above `depositMin` that
  failed the screen, drawn through `MapView.project` on a new `#markers` overlay in 0.6.2. This
  layer does not exist in 0.6.0; it appears only after an explicit regional campaign. A `Kinds`
  select filters the overlay and summary (`all` by default). To bound redraw cost, show at most
  1,536 viable and 512 nonviable markers, sampled evenly in catalogue cell order when a class has
  more records than its share; the panel reports shown/total counts so omissions are explicit.
- **Exports**: the campaign's `Export deposits` writes the discovered records in the existing v2
  format, filtered by the session ledger and current kind filter. `totals.contained` remains the
  sum for all exported records; `totals.viableContained` is the same exact sum the summary labels
  `contained` (viable records only). The full `Deposits JSON` control remains the explicit
  all-catalogue export; there is no third schema.

Two deliberate choices:

1. **The local click loop stays primary.** Most questions concern one pointed-to cell; the campaign
   is an explicit broad sweep for players who need it, never a default, pre-check or hidden cost of
   local reports.
2. **The campaign uses the player's instruments.** The map is a survey, not an oracle: nothing
   appears that no checked instrument could find, and every marker inherits the confidence its
   discovery reached.

## 3. Cost

- Core: O(beds + bodies) ≈ tens of operations; text formatting allocates once per click.
- Campaign: one explicit O(V) catalogue build, then bounded surveys of at most 256 cells and a
  1.25 ms time slice per animation frame (checked every eight cells). The budget is based on the
  measured local survey cost, not the number of cells in the world; the catalogue build never
  repeats per chunk. The L5/L7 build and per-chunk measurements are recorded in §3's calibration
  note when the increment is measured.
- Markers: at most 2,048 glyphs are redrawn on a map/view/filter/result change (no all-cell or
  catalogue scan in the ordinary frame loop). A pan projects only the bounded displayed set, and
  the overlay is absent until an explicit campaign or a partial campaign cancellation.
- **Calibration (sandbox, Node, seed 7)**: one standalone catalogue build measured 8.12 ms at L5
  (10,242 cells) and 52.39 ms at L7 (163,842 cells); its t=0 startup world had 0 records, and
  setup/raster time is excluded. The L5 build smoke in the test suite reported 10–21 ms across
  runs. Twelve warmed L5 campaign chunks using `d500,geo,mag` had repeated medians of 1.28–1.40 ms
  against the 1.25 ms target, with the timer polled every eight cells. The campaign unit test spies
  on `Deposits.build` to confirm it is not re-entered by chunks or filter/export actions.

## 4. Tests

`tests/core.js` (new):

1. **Bookkeeping** — layers are contiguous from surface datum to requested depth, or to the
   quantized Moho for `to basement`; thicknesses are nonnegative, their sum is the logged depth,
   and the seawater interval exists exactly when `z < Params.sea`.
2. **One record, two holes** — a synthetic column whose actual `arc` catalogue record has bodies
   intersecting a 5 km hole marks the interval there and not in a 500 m hole; each interval's `id`
   and grade equal the record's, with the water-depth offset on a wet column.
3. **Overlay integrity** — overlapping synthetic bodies stay on one contiguous host interval
   while every record id/grade is retained; the real catalogue record's intersected body is
   represented by contiguous `oreRecords[]` segments.
4. **Context beds** — `coal` only with a coal record or the land-basin signal, `gravel` only with a
   placer record (or the `oPla` + downhill test), `U-bearing` only with a uranium record; none of
   them on a cell whose context fails.
5. **Determinism** — two calls identical; identical after a checkpoint round trip; a body-carrying
   column that moves a cell keeps its bedding.
6. **Text and JSON** — the text has one header plus one line per layer, the JSON parses with
   `format: 'pgt-core'` and `version: 1`, and a free-depth request (`to basement`) ends at the Moho.

`tests/longrun.js` (full profile, owner-rig release gate) additionally checks every catalogue body
at every record cell on the evolved 1500 Myr L5 snapshot: wet-datum conversion, full-body coverage
by contiguous `oreRecords[]` overlays, and exact agreement between local core intersections and the
regional catalogue. `--release` performs the same check on its 4500 Myr coarse history.

`tests/instruments.js` (extended): campaign progress is monotone; fixed-size chunks produce the
same ledger as a straight ascending-cell loop; repeated campaigns are deterministic; cancel leaves
a valid partial ledger; an empty set refuses; and a frame/epoch change aborts rather than mixing
snapshots. A timed L5 chunk measurement pins the production budget.

`tests/gui.js` (extended): `Survey all cells · build viable map` refuses with an empty instrument
set and performs no build, starts only after an explicit click, pauses playback, progresses in the
stub's frame loop, cancels cleanly, marks a snapshot stale, filters summary and markers by `Kinds`,
and exports the `pgt-core` and filtered `pgt-deposits` tags. `?inst=…&depkind=…&core=5k` prefills
choices but never starts a campaign. The capture line gains campaign counts only after a campaign
has run. A UI spy confirms initial load and ordinary hover/click do no regional build.

## 5. Order and acceptance

Order: `Core.section` + text (reads local records, no UI) → the pinned report's core block →
explicit `campaign` chunked over frames with the progress line → summary + markers + exports →
tests. Local click-to-survey remains available throughout and never waits for or starts a campaign.

Acceptance:

1. **Local first; regional only by request**: a fresh load performs no all-cell work; a one-cell
   click evaluates only its footprint. The labelled regional button applies the selected
   instruments to every cell only after an explicit click; with no instrument checked it refuses.
2. **Totals are exact**: the summary's contained metal equals an independent sum over
   `Deposits.viable(state)` filtered by the ledger, to the tonne (the test recomputes it from the
   records, not from the summary).
3. **Frame budget**: the UI requests at most 256 cells and a 1.25 ms slice once per animation
   frame, with time checked every eight cells; warmed L5 chunk median is below 1.5 ms (timing
   outliers are measured rather than represented as a hard real-time guarantee), and the catalogue
   is not rebuilt per chunk. A campaign pauses playback instead of sharing a play frame.
4. **The core and the catalogue agree** for every record cell on the evolved 1500 Myr L5 snapshot,
   checked by the full-profile `tests/longrun.js` test (the long profile is not run in this sandbox).
5. **No engine work**: `git diff` for the increment touches no file under `js/gpu/`, no WGSL
   source, and `js/render.js` only for `MapView.project`; run the parity harness and short profile
   in the sandbox, then run `ores`/`longrun` on the owner rig before release. Fill the calibration
   table in `0.6.1` §10 from that release run.
6. **A capture restores choices without surprise work**: `?inst=…&depkind=…&core=5k` restores
   instrument selection, filter and hole depth, but never starts a campaign on page load. The user
   must explicitly start a regional sweep again.
