# 0.6.4 review — the discovery ledger as a first-class map view

## 1. Review scope

The commit under review is `bb3e652`, "0.6.4 discovery ledger: local finds on the map without a
campaign, marker and row pin selection, sortable ledger list, drilled field band and global
largest printed, review follow-ups closed". Its surface is small and its state is not: the
session ledger became the source for two views (the marker overlay and a sortable row list), one
selection (marker ⇄ row ⇄ panel), and a fourth place where a record's grade can be read.

Reviewed by reading those paths — `Instruments.Ledger` and its index maintenance,
`findEntry`/`removeEntry`/`reconcile`, `refreshLedgerMarkers`/`refreshLedgerRows`/
`paintDepositMarkers`/`hitDeposit`, `finalizeCampaign`, and the two grade printers — and then
reproducing every suspicion against the real modules rather than arguing about it. Baseline
before any change: `node tests/run-all.js` → **PASS, 36 tests, 163 s**.

The rest of the commit holds up. The overlay really is ledger-backed (a local find is on the map
with no campaign), the marker hit cache mirrors what was painted, the painter and the click
resolve in the same projected space with the seam wrapped, `sampleMarkerClass` samples by kind
quota with a largest-remainder allocation, the drilled field band and the lab certification are
two axes and the report says which one it is printing, and `summary.top` is a bounded
insertion-sorted ladder rather than a full sort per summary. Nothing there had to be undone.

## 2. Four defects, each reproduced before it was fixed

### 2.1 "found order" stopped being the order things were found

`Ledger.found` is a swap-pop list: `removeEntry` moves the last entry into the freed slot and
rewrites its `ledgerIndex`. The list sorted by `ledgerIndex`, so one retirement reorders the
history. Four isolated placer columns at L3, surveyed in order, then the first one dropped below
the hysteresis floor:

```
creation order:   3a116aa3 7ae3582b 5cf24864 60d754ea
sorted by slot:   60d754ea 7ae3582b 5cf24864     <- the last-found record now leads
survivors, truly: 7ae3582b 5cf24864 60d754ea
```

The ledger now hands out a `serial` per discovery, assigned once and never reused, and the list
sorts (and breaks ties) by that. `ledgerIndex` stays what it always should have been: the entry's
position in the array, used only by `removeEntry`.

### 2.2 A retired record left its pin behind

`selectedDeposit` holds a record id. Nothing cleared it when the record left the ledger, and the
id is a hash of (seed, class, plate-frame anchor) — so the same deposit, found again later, comes
back **already selected**, and the first click on it releases a pin the user never saw instead of
setting one. Two clicks to pin a deposit that retired and returned.

`refreshLedgerRows` is the one place every ledger mutation reaches, so the pin is dropped there.

### 2.3 A regional campaign retires records and the list did not follow

`surveyInternal` calls `reconcile` on every cell it touches, campaign or not, so a sweep both
adds and retires discoveries. `finalizeCampaign` refreshed the campaign view and the marker
overlay but not the row list: retired rows stayed on screen, and campaign discoveries did not
appear until the next local click or filter change. `finalizeCampaign` now refreshes the rows
too. (It refreshes once, at the end. Refreshing per chunk would rebuild 200 buttons 40–640 times
per campaign for a list the user cannot read while it is moving; the progress line carries the
counts meanwhile.)

### 2.4 The lab certified a core that was never drilled

`applyLab` set `assayed` on any record it upgraded, drilled or not. A record found from the
surface has no core, so there was nothing to assay, and the two printers disagreed about it:

```
pinned panel:   #4934bd05 placer indicated 20-166 m continental · lab assayed
survey report:  #4934bd05 placer indicated ... · lab inferred → indicated      (no assay line)
```

`depositText` is documented as "one deposit reads identically wherever it is opened". `assayed`
now means what it is used for — a drilled intersection whose field band became a certified grade
— and an undrilled record gains confidence only.

### 2.5 One documentation defect

`README.md` (twice), `AGENTS.md` and `0.7-proposed.md` all point at
`0.6.3-merge-comparison.md`; the file is `0.6.3-2-merge-comparison.md`, and its own title is
"0.6.3 — merging two independent implementations". The file was renamed to the name every
reference and its title already use.

## 3. One behaviour change without a regression test

`hitDeposit` returned the first painted marker within 7 px, and non-viable markers are painted —
and therefore registered — before viable ones. Several records share a cell, so their diamonds
land a few pixels apart and a click on a filled viable marker could pin the hollow sub-economic
one under it. The click now resolves to the nearest marker, with the filled one winning an exact
tie, which is the diamond actually on top. No test: the DOM stub has no fixture with two
overlapping markers of opposite viability, and building one would assert the tie-break against
itself. The change is a strict narrowing of which marker a click means.

## 4. What the tests now cover

Each fix was checked by putting the old behaviour back and watching the suite fail:

| fix | restored defect | failing assertion |
| --- | --- | --- |
| serial-based found order | sort by `ledgerIndex` | `and the discoveries that predate the sweep keep their found order across the reused slot` |
| pin released on retirement | drop the guard in `refreshLedgerRows` | `without coming back already selected` |
| list follows the ledger at campaign end | drop the `refreshLedgerRows` in `finalizeCampaign` | `the record the sweep retired leaves the list` |
| lab certifies cores only | re-add the undrilled `assayed` branch | `lab certifies a core: a record found from the surface has nothing to assay` |

`tests/instruments.js` gains the ledger-level half (six kinds on one cell, retire the first, found
order survives; an undrilled record stays unassayed and both printers agree). `tests/gui.js` gains
the page-level half on the ledger fixture plus one small fixture of its own, so the pin case is
driven through a real click sequence: pin a row, retire the record under a running sweep (whose
overlay is hidden, so no click can release the pin on the way past), find it again, and require
that it is an ordinary unselected record.

After the changes: `node tests/run-all.js` → **PASS, 37 tests, 150 s**. The 37th test is
`tests/heightfield.js` from the 0.5.6 slice in the same session, not from this review.
