# 0.6.x — Deposit prospector: umbrella plan

Turns the on-demand deposit extraction (`js/extract.js`, design §8) into a local prospecting loop:
select instruments, click one cell, inspect its readings and keep the report pinned while the normal
column probe follows the pointer. Later increments enrich those clicked-cell findings with stable
size, grade, depth and contained-metal records anchored to Earth grade–tonnage ranges, plus a
synthetic stratigraphic core. An optional, explicit regional campaign and viable map may follow;
scanning every cell is not the default exploration action.

Written to stand alone. This file owns the vocabulary, the determinism contract and the staging;
the three increments carry the detail:

| file | increment | ships |
|---|---|---|
| `0.6.0-plan-instruments.md` | instruments + local survey | instrument table, single-cell click-to-explore loop, pinned report, session ledger; no map-wide scan or marker layer |
| `0.6.1-plan-deposit-catalogue.md` | catalogue + economics | local deposit records, quantization/stability, the Earth-anchored class table, viability, JSON export |
| `0.6.2-plan-core-and-viability-map.md` | core + optional regional view | stratigraphic core log, explicit campaign and opt-in viable map, resource summary, exports |

Scope decided with the owner: **prospecting only**. No money, no claims, no extraction, no mining
simulation — "commercially viable" is the industry's own grade / size / depth screen, not a cash
flow. The records in this increment are the data contract a later economy increment consumes.

## 1. What already exists, and what it does not answer

The sim keeps six saturating potentials per column (`oVms oMaf oArc oOro oBas oPla`, 0..1) plus
`fert`, the host thicknesses (`hFel hMaf hSed`), `age`, `damage` and the cell fields derived from
them (`z`, `wet`, `slope`, `low`, mobile sediment `m mFel p`). `Extract` blurs one potential by one
cell, takes its local maxima above a threshold, ranks them, tags each with host / depth / age /
epoch / plate / lat and dumps JSON.

That answers "where is the strongest signal". It does not answer, and the draft asks for:

1. **What did the player measure, and with what?** One undifferentiated "deposit" list is the same
   information whether the player looked at an outcrop or drilled a 5 km hole.
2. **The same deposit twice.** The current list is deterministic for one frozen state, but a local
   maximum can hop a cell when the field drifts, and every number in it moves continuously with the
   potentials — so a re-click at a slightly different frame tells a slightly different story, and a
   capture cannot be compared to the last one.
3. **Size, grade and depth in units a geologist recognises**, not a 0..1 potential.
4. **A core.** The draft asks for a stratigraphic column — the drill is also the readable record.
5. **An optional regional answer** (0.6.2): which deposits are worth anything, summarized by commodity, when the user explicitly starts a campaign. This complements rather than replaces one-cell exploration.
6. **Noise control**: not every cell may host a rich deposit; a threshold has to separate the
   interesting few from the background without hiding the arc that is genuinely forming.

## 2. The model in one page

```
truth                 catalogue (0.6.1)              survey (0.6.0)                 output
─────────────────────────────────────────────────────────────────────────────────────────────
columns:              local candidates:               one instrument set + click:     pinned report
  potentials  ──────▶ blurred value ──▶ records ────▶ reading, detection,   ──────▶ JSON / core
  hFel/hMaf/hSed       ≥ threshold       tonnage       confidence, ranges            optional map
  z / wet / age        local maxima      grade                                        (0.6.2)
  body (plate frame)   quantized         depth
```

- **Truth** stays exactly what it is: six potentials on Lagrangian columns, carried by the plates.
  No new sim state, no checkpoint change, no frame cost.
- **The catalogue** is a pure function of the sim state plus the seed: blurred potentials →
  ranked local maxima → one record each, whose tonnage, grade, geometry, depth and contained metal
  come out of a flat class table (`Deposits.CLASSES`) and an integer hash of the record's *anchor*
  (class + quantized body direction). Everything is quantized before it becomes a number, so the
  catalogue is byte-stable under irrelevant drift.
- **The survey** is a set of instruments, each with a reach, a footprint and a detection limit. A
  click returns the instrument readings for that cell and the records that instrument set can
  detect, with a confidence level. The *only* mutable exploration state is the session ledger
  (which cells were surveyed, which records were found) — page-local, never checkpointed.
- **Output**: a report pinned to the last clicked cell, core text and JSON exports. An overlay of
  viable records belongs to the later opt-in regional-map increment, not the single-cell workflow.

## 3. The stability contract

This is the answer to "generate deposits to be more or less stable across different calls and
time", stated as rules the tests can hold:

| # | rule |
|---|---|
| S1 | **Quantize before converting.** A record's numbers are functions of integer buckets — potential `floor(255·v)`, depths to 50 m, grades to two significant figures through a log table, tonnage on a 1-2-5 ladder — so a change smaller than one bucket changes nothing at all. |
| S2 | **No clock, no RNG.** Nothing in a record reads `state.t`, `state.frame` or `Math.random`. Instruments' noise is an integer hash of `(seed, class, anchorKey, instrument)`, in the style of `Contact.hash` but never keyed on the frame. |
| S3 | **The anchor is physical.** A record's identity is `(class, quantize(column.body, 2⁻¹⁵))`. `body` is fixed in the plate frame and survives rigid motion and column compaction exactly; it changes only when a plate merge or a terrane rebase rewrites columns into another frame — documented, and re-associated by proximity (S5). |
| S4 | **Saturation and decay are already slow.** Potentials move by `(1−o)`-scaled rates of a few 1e-2 per Myr at dt 0.1, so at normal play a record's buckets hold for many frames; the threshold plus the one-cell blur is what stops flicker at the boundary. |
| S5 | **The ledger grants persistence.** Once a survey has found a record, it stays found while the blurred value is ≥ 0.7× the detection threshold (hysteresis). A merge that changes the anchor keeps the discovery, re-associated by class and world position within 1.5 cells. |
| S6 | **A map is a snapshot.** Every map, export and panel header carries `epochMyr`; when `state.t` has moved more than 5 Myr the UI marks the map stale and offers a rebuild. Nothing claims a 1500 Myr map is current at 3000 Myr. |

S1–S3 give the same answer to the same question; S5–S6 give the answer the player expects over
time. Both are cheap: no sim change, no per-frame work.

## 4. Thresholds — the three levels

The draft's "not all cells should have rich, commercially valuable deposits" is three separate
gates, and conflating them is what makes an ore map unreadable:

1. **Anomaly** — blurred potential ≥ `traceMin` (0.15, today's `Extract` default). Shown as an
   instrument reading, never as a deposit record. This is the noise floor.
2. **Deposit** — blurred potential ≥ `depositMin` (0.30) *and* a local maximum under the one-cell
   blur. A catalogue record exists. Below this the potential is still real geology (the factory is
   running) but too weak to be a named deposit.
3. **Viable** — the record passes the class's economic screen: grade ≥ cut-off, tonnage ≥ minimum
   size, depth ≤ maximum mining depth. The map button and the summary use this level only.

`depositMin` and the class table's cut-offs are committed in `js/params.js` /`Deposits.CLASSES` and
are tuning constants with tests, not guesses in the UI code.

## 5. Where the deposits come from, in the player's language

The six potentials exist because the sim already has the right factories: ocean-ridge and arc VMS,
plume and rift mafic systems, subduction arcs, collision belts, subsiding basins, and erosion-fed
placers. The catalogue maps each to a commodity group with real Earth ranges — porphyry Cu-Mo-Au,
VMS Cu-Zn-Pb-Ag, magmatic Ni-Cu-PGE (plus cratonic diamonds), orogenic Au and sediment-hosted Au,
sandstone uranium / coal / potash, placer Au, and a derived BIF-hosted iron. The exact table, with
the sources its numbers came from, is `0.6.1-plan-deposit-catalogue.md` §2.

Two vocabulary decisions that everything else depends on:

- **A record is a cluster, not an ore body.** One L5 cell is ~223 km across, four orders of
  magnitude larger than a porphyry stock. A record therefore describes the *prospect/cluster* the
  cell's anomaly stands for: 1–8 bodies whose combined tonnage is compared to the published
  per-deposit percentiles scaled by the expected cluster size. The bodies matter: the core and the
  drill intersection read them, and the test that geometry reproduces tonnage keeps the record
  internally consistent instead of decorative.
- **Depth is depth below the surface.** `top` = the class's emplacement-depth band (hashed,
  quantized) + present sediment cover `min(hSed, cap)`. `surfaceZ` carries the elevation or the
  water depth so a seabed massive sulfide is reported as such. The one simplification is stated
  where it matters: the sim keeps no denudation history, so the catalogue does not claim a deposit
  has been eroded out (a hook for a later increment, catalogue plan §7).

## 6. Module map and load order

| file | contents | loaded |
|---|---|---|
| `js/extract.js` | **unchanged**: `blur`, `peaks`, `host`, `compare` — the field primitives | before deposits |
| `js/deposits.js` | `Deposits.CLASSES`, `build`, `at`, `viable`, `summary`, `json`, the quantization helpers, the cache | after extract |
| `js/instruments.js` | `Instruments.LIST`, `survey`, `Ledger` (coverage + found + hysteresis), `report`, `json` | after deposits |
| `js/core.js` | `Core.section`, `Core.text`, `Core.json` | after deposits |
| `js/ui.js` | instrument controls, separate pinned report, click hook, URL prefill and capture line; optional map UI later | last |

Each new module is a classic script with node-guarded `module.exports`, added to `index.html` and
to the `tests/browser-scripts.js` load list when its increment lands. The local survey UI needs no
renderer or GPU-kernel changes. The optional regional map, if retained after single-cell use has
been evaluated, belongs to 0.6.2 and may use an engine-neutral overlay without changing simulation
state or compute kernels.

## 7. UI surface

The local prospecting controls use a fieldset distinct from the report: seven instrument
checkboxes and a clear “click a cell to survey it” hint; a separate scrollable `<pre id="prospect">`
shows the last clicked cell's result. The ordinary `#probe` remains a cheap pointer-follow view.
Controls for a regional campaign, viable map, and exports belong to their later increments and are
not default-on.

- A **click** on the map keeps its current meaning (probe the column) and, when at least one
  instrument is checked, additionally surveys the cell. **Hover** never surveys and never moves or
  clears the pinned report.
- With no instrument checked the page behaves exactly as before: this increment adds no default-on
  behaviour, and the short test profile's GUI pins stay valid.
- URL prefill follows the existing vocabulary: `?inst=obs,geo,d5k&core=5k`. The capture header
  records the selected instruments only when that set is non-empty; regional-map settings are
  captured only when that later feature is added.

## 8. Tests and gates

New: `tests/deposits.js`, `tests/instruments.js`, `tests/core.js` (short profile — all three are
pure and fast). Extended: `tests/ores.js` (its extraction block moves to the v2 record),
`tests/gui.js` (controls, click → local survey, pinned report, prefill and GPU event capture),
`tests/browser-scripts.js` (new script tags and format tags). Optional regional-campaign tests are
added only with that increment. Untouched by construction: `tests/wgsl-struct.js`,
`tests/gpu-parity*.js`, `tests/render3d.js`.

The increments' acceptance criteria are in their own closing sections. The umbrella gate is the
short profile green plus a measured pass over a 1500 Myr L5 hot start that records, in the
calibration table of `0.6.1-plan-deposit-catalogue.md` §10, the viable-record counts and the
per-class median tonnage and grade — the numbers a later increment compares against Earth.

## 9. What this is not

- **Not an economy.** No prices, costs, royalties or claims; viability is a static screen. The
  reference values used as cut-offs are calibration constants with sources, not a currency.
- **Not a reserve estimate.** Records are *resources* in the geological sense, in the same spirit
  as the grade–tonnage models they are anchored to, with the confidence level named.
- **Not a mining simulation.** Nothing is removed from the sim by exploring it; a deposit stays a
  fossil in the column wherever the plate carries it.
- **Not per-frame.** The catalogue is built on demand and cached; the catalogue plan's budget
  section measures the build at L5 and L7 and states the rule (never inside the frame loop).
- **Not hydrocarbons.** `oBas` covers U / coal / potash; oil and gas in-place volumes are out of
  scope at 223 km cells, recorded as a hook rather than faked (`0.6.1` §7).

## 10. The live-evolution gate (explicit, currently closed)

`0.5.5-followup-review.md` asked for an explicit gate on whether deposits evolve *live*, so it is
stated here rather than left implicit in the S-rules: **the deposited catalogue is a pure function
of the state, and 0.6.x keeps it derived.** The potentials already carry the only evolution the sim
models — production, saturation and a 500 Myr decay — and the plates carry the deposits with them;
nothing about a record changes except through those fields, so a second entity that copies them
would be a cache with a correctness risk, not a simulation.

Reopening the gate means deciding for one of three drivers, each with a price that is known now:

| driver | what it needs | price |
|---|---|---|
| mining / depletion (a later economy increment) | persistent deposit entities with a remaining-tonnage field | a new column field + `Checkpoint` VERSION bump |
| deposits destroyed by erosion or subduction | a `denudation` column field fed by the existing erosion flux, and record lifetime rules | a new kernel output, a new test rig, the catalogue's §7.1 hook closed |
| live growth of an ore body (remobilisation, supergene enrichment) | a `Deposits.cycle` at the 1 Myr cadence beside `Events.cycle` | O(records) per Myr, a checkpoint slice, and a CPU/GPU story if it must run on the device path |

Until one of those is chosen, the gate stays closed and S1–S6 are the contract: same state, same
catalogue; same question, same answer. Choosing it later is a new increment with its own plan —
not a quiet change here.

## 11. Order

`0.6.0` first because the click-driven ledger and pinned report are the common exploration loop,
then `0.6.1` enriches its local findings into a stable catalogue and `0.6.2` adds the core plus an
optional regional campaign/map. Each increment is shippable alone and leaves the page working; the
local click workflow remains the primary interaction throughout.
