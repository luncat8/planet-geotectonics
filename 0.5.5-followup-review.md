## Findings, highest priority first

### P1 — proposed ring gather cannot deliver the stated interpolation contract

The commit's `0.5.0-plan-3d-render.md` §14.3–14.4 promises C1 continuity, exact
cell-centre values, no new GPU allocation and sub-millisecond timing for one-ring
Wendland blending. These are not established:
- Switching nearest cells switches contributor sets. Nonzero omitted weights can
  cause discontinuities even when each individual kernel is smooth.
- A normalized finite weighted average generally smooths a sample centre instead of
  reproducing its value. IDW and finite RBF averaging are not interchangeable guarantees.
- The CPU simulation's 3D session has neither uploaded adjacency nor positions to
  borrow; `GRIDI` alone would not supply positions on the GPU path either.
- No device measurement supports the timing table.

**Disposition:** replace §14 with a C0 barycentric prototype/implementation plan, explicit
lookup cost, invalid-height handling, numeric tests and measured device gates. Continuous
gradients are not a release promise. Preserve existing hex sampling as the initial default.

### P2 — inherited analytic-normal seam reads survive the pole fix

In `js/render3d.js`, `NORM_ANALYTIC` used `x = floor(uv.x * W - 0.5)` without wrapping
the centre. At uv.x = 0, x = -1: the north/south taps are out of bounds and the west
neighbour is wrong. At uv.x = 1, x = W−1: all taps differ from the other representation
of the same longitude. This can produce a lighting seam in analytic mode, including
on the duplicated lattice seam. It predates the reviewed commit; the pole guard does
not address it.

**Disposition:** wrap the centre before deriving neighbours. Both seam endpoints now
use `(W−2, W−1, 0)`. Add tests evaluating the shader's actual integer-index expressions
at seam endpoints and interior longitudes, plus a source pin. These are numerical/index
tests, not shader execution or pixel tests. Add seam inspection to the next rig check.

### P2 — prospecting needs a new data contract, not a renamed potential export

`js/state.js` describes six saturating potentials, while `js/extract.js` exports
resolution-dependent local peaks and `depth = -surface elevation`. Neither is a
concentration or buried body. `js/events.js` compacts columns, so column indices
cannot serve as lasting deposit IDs. A click-seeded maximum extractor would change
bodies as the view/time/resolution changes and could mislabel altitude as drill depth.

**Disposition:** the new 0.6.x plan separates snapshot, deterministic bodies and survey
knowledge, defines burial/altitude/water depth, grade/tonnage units, economic assumptions
and a frozen-scenario MVP. Live evolution explicitly requires lifecycle identity and
checkpoint/CPU–GPU changes rather than pretending the first version already tracks it.

### P2 — proposed resolution/L8 ladder understates state and device requirements

`Earth.apply` is a pack seeder with plate initialization and ledger rebasing, not a live
state remapper. Surface RMS alone cannot establish conservation. `GpuSim.layout` uses
83 f32/cell for gridF: L8 needs roughly 207.5 MiB in that one binding, exceeding the
common 128 MiB limit. The original roadmap also incorrectly included release-only
checks in the default `run_full_test.py` command.

**Disposition:** move resolution to 0.7.0 as requested, require conservative transactional
transfer, gate L8 on device limits and memory, and distinguish full from --release.

## What is sound in the commit

The analytic pole guard prevents normalization of a zero tangent basis, and destroying
the timestamp resolve/map buffers closes an ownership omission. Keep both fixes.
The guard returns a radial approximation over a small cap (about 0.81° from each pole),
not an exact normal of arbitrary polar relief; exact pole normals are not necessarily
radial. Its visual transition remains a rig judgement, not evidence of physical accuracy.
The added buffer tests exercise cleanup using mock resources, not actual timestamp
mapping or GPU lifetime behaviour.
