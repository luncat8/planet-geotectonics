## Verdict

This is a **good, coherent merge**, but not a literal “best of both branches.” The alternate branch is a sensible trunk: one catalogue model supports more deposit types, stable column-frame identity, the core and regional campaign. The merge also retained reflection seismic and the separate price scenario. Choosing one catalogue rather than trying to combine two incompatible identity models was the right architectural call.

The trade-off is real, though: the other branch’s ellipsoid geometry was discarded. The merge notes acknowledge that loss (`0.6.3-merge-comparison.md:148–167`). I’d keep the current catalogue as the source of deposit classes and identity, but consider recovering the useful geometry ideas as a separate layer—not restoring the old generator wholesale.

**Scope note:** this checkout is shallow and doesn’t contain the two source branches, so I couldn’t independently diff their trees. This assessment uses the committed comparison document, the resulting code and the tests.

## Main review findings

1. **Drill confidence currently overstates the evidence.** A direct drill hit sets confidence to `measured` (`js/instruments.js:351–356`), while the same report says “assay pending” (`js/instruments.js:600–603`). A single hit also establishes an intersection, not a measured resource in the geological sense. I’d keep drilling as direct evidence, make assay a meaningful follow-up, and reserve “measured” for more complete sampling evidence—or label the confidence scale explicitly as a game abstraction.

2. **A core hit is only a depth-interval test, not a spatial intersection.** Records store body depth, footprint area and thickness, but no horizontal position or orientation (`js/deposits.js:366–375`). Core intersections test only the vertical interval (`js/core.js:199–205`); drill reach likewise checks the deposit’s top depth (`js/instruments.js:164–173`). So the model effectively assumes the drill is over each body in its cluster. That’s acceptable for a simplified prospectivity prototype, but not for realistic drill results. A deterministic body position, strike/dip and a simple ray/solid intersection would make a meaningful next realism improvement.

3. **The deposit map is useful, but not yet an explorer UI.** The regional campaign already has valuable pieces—explicit opt-in, progress/cancel, a kind filter, exports, and a top-ten list per kind. But discoveries from local clicks don’t appear on the map unless there’s a campaign view (`js/ui.js:573–585`, `1298–1307`). And the marker overlay is deliberately non-interactive (`style.css:26–27`), so markers can’t be selected to open a record. The summary is a long text report, not a browsable list. I’d add a ledger-backed map layer for local discoveries and a sortable results list whose rows and markers select/focus a deposit. Include a global “largest” view as well as per-kind ranking.

   One location detail to fix as part of that: records save their physical direction, but campaign markers project the grid cell centre (`js/deposits.js:403–410`, `js/ui.js:857–861`). Using the saved direction would better match the anchored deposit location.

4. **Campaign setup still has a synchronous pause.** Survey work is time-sliced, but `Deposits.build` runs synchronously before it starts (`js/ui.js:931–940`, `js/deposits.js:473–517`). The README reports 21 ms at L5 and 74 ms at L7 (`README.md:52–54`), enough to visibly stall a frame at the higher level. Also, my short-test run measured the campaign chunk median at **1.31 ms vs the 1.25 ms target**; the merge log reports 1.34 ms. That’s a small miss, not a failing suite, but it should be treated as a miss. Profile the catalogue build separately and either time-slice it too or set a measured, user-visible preparation budget.

5. **The realism claims need careful framing and better calibration.** `data/deposits/SOURCES.md:3–8` says the values are game parameters and no distributions have been fitted; some rows also rely on broad literature or explicit assumptions (`:19–32`). There has been useful source-based checking and tuning, but this is not yet an empirical fit to deposit populations. Likewise, the core generates deterministic synthetic lithology from a hash (`js/core.js:52–58`). I’d describe outputs as **modeled prospects / synthetic core logs**, not actual reserves or measured ground truth. A later fidelity pass can fit class distributions against the cited datasets and improve body geometry and lifecycle assumptions.

6. **The roadmap needs a refresh.** `0.7-proposed.md:20–31` still lists 0.6.2 as an economic filter and 0.6.3 as live deposit evolution; its “Next implementation slices” still asks for instruments that are already shipped (`:121–128`). The status note explains some of this, but it’s not a reliable plan for the next work.

One smaller hardening item: public deposit IDs are 32-bit hashes (`js/deposits.js:135–145`) and the session ledger keys by ID. Collisions are unlikely at the current L5 scale, but the risk grows with catalogue size; add an L7 uniqueness assertion or move to a wider/composite identity before scaling up.

## Economy and recommended next steps

The current price module is **not a game economy**: it has no mining, depletion, inventory or market simulation. It is a static valuation scenario. But it is printed on every found report and recalculated in summaries (`js/instruments.js:639–650`, `js/deposits.js:564–594`), so it adds UI noise for your current priorities. I’d freeze it as an optional sidecar and remove or hide the money lines by default—no economy work in the next milestones.

I’d proceed in this order:

1. **Hardening and performance:** validate campaign/reset/snapshot behaviour across L5–L7, measure build and chunk budgets, add catalogue ID-uniqueness checks, and resolve the drill-confidence/assay mismatch. Run the full/release and real-device GPU gates on the owner rig before claiming those paths are stable.
2. **Deposit realism:** add spatial body geometry and real intersection tests; calibrate class distributions and detection assumptions against held-out data; make synthetic versus model-derived results explicit.
3. **Discovery UX:** show locally discovered records without requiring a whole-world campaign; add selectable markers and a sortable results list for discovered, viable and largest prospects. Keep broad campaigns deliberate, not automatic.
4. **Defer live resolution changes and any actual economy** until those foundations are solid.

The architecture’s strongest choices—derived catalogue, deterministic anchors, a session-only ledger, and explicit snapshot-bound campaigns—are worth keeping. I would improve the model and discovery workflow around them rather than undertake a broad rewrite.
