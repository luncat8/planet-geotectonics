### 1. The 32 errors named themselves, and the name is a Chrome/D3D fact

```
[Texture "D3DImageBacking_D3DSharedImage_WebGPUSwapBufferProvider_Pid:17956"]
usage (TextureUsage::(TextureBinding|RenderAttachment)) doesn't include TextureUsage::CopySrc.
 - While validating source [...] - While finishing [CommandEncoder (unlabeled)].
[Invalid CommandBuffer] is invalid due to a previous error.
```

Two per layer, sixteen layers. Phase I4's fix — ask the canvas for `COPY_SRC`
with `configure({ usage })`, then copy out of `getCurrentTexture()` — does not
work on a presented canvas: Chrome backs it with a D3D shared image whose usage
the swapchain picks, and the request is ignored. A software adapter honours it,
which is exactly why the headless rig looked fine and the copy died on your
machine. The empty comparison that followed is the same failure the previous
session half-fixed: the staging buffer kept its zeros, and `mean|d| NaN max|d| 0`
is a line nobody can interpret (`max|d| 0` says every difference compared false,
`NaN` says the quotient was 0/0 — with two byte arrays, neither is reachable from
the code as written).

So the readback never touches the canvas now. `GpuRenderer.init(state,
{ readback: true })` draws the layer into its own `RENDER_ATTACHMENT|COPY_SRC`
texture, copies that into a reused staging buffer (`readPixels()`), and blits it
to the canvas with one nearest-sampled fullscreen triangle — so the pixels the
gate compares and the map you see are the same bytes. The app's renderer is
untouched: default canvas usage, one pass, no offscreen texture, no staging.
`tests/gpu-readback.js` (new, in `run-all.js`) pins that split on the stub device
by recording commands: `configure` carries no usage, the texture is
`RENDER_ATTACHMENT|COPY_SRC`, the order in one submit is draw → blit, the copy is
its own submit and its source is never the canvas.

Phase 4 also reports its inputs now — `ch>16: N · M samples` per layer, the mean
divided by the samples actually compared, and a setup failure that prints all
three sizes (canvas / readback / CPU reference) instead of silently comparing
nothing. A throw anywhere in the readback path is caught and reported, so phases
1–3 and the error list still make it into the log.

### 2. D1 is a measurement now, and the device reports it

Your capture is what settled the direction:

```
[parity] omega relaxation: mean |omega|/|omegaTarget| cpu 0.837 gpu 0.973 over 16 plates
         · p1 cpu 0.943 gpu 0.991 · p2 cpu 0.691 gpu 0.966 · p3 cpu 0.871 gpu 0.828 · p4 cpu 0.863 gpu 1.167
```

The device's ω sits on the unrelaxed fit (0.973, and p4 is *above* its own target
— something α = 0.2 can only do by inheriting a larger ω from the frame before),
the CPU's lags it (0.837), and the speeds follow: gpu 4.947/13.026 against
cpu-from-target 5.040/13.052 and cpu-from-relaxed 4.022/11.449. `reduceB` is
line-for-line `Plates.reduce`, `P_TAUOMEGA` is literally `0.5` in the generated
source (I printed it), and the previous session already ruled out the flags, the
accessors and the dispatch. Reading code has nothing left to give, so I stopped
reading and made the kernel talk:

- `reduceB` leaves one witness per plate in the reduce scratch —
  `|ω_stored − (ω_prev + (fit − ω_prev)·α)|`, reading ω *back* out of the buffer,
  because the question is what is in the buffer.
- `zeroFrame` clears that region (its shape is now `GpuSim.zeroThreads(l)`, one
  source for the kernel's branches and the dispatch count), so a frame that never
  runs K10 reports 0 rather than the previous frame or uninitialized scratch.
  `GpuSim.raster` opens with `zeroFrame` for the same reason — the boot diagB was
  folding whatever the scratch was born with.
- `diagB` folds the witnesses into `DIAG[D_RELAXERR]` and reports `D_DT`/`D_ALPHA`
  — the dt and α the *same* frame ran with, derived from the `frameIn` K10 read.
- `pull` mirrors slots 14..16 to `state.gpuDt`/`gpuAlpha`/`gpuRelaxErr`, and the
  smoke prints a `device K10:` line and fails with four different sentences:
  the device ran a dt the JS did not upload · the device's α is not
  `min(1, dt/τ_ω)` · the stored ω is not the relaxed ω · the device carries the
  fit while all three of those say the relaxation ran. (Compared at f32 — 0.1
  arrives as 0.10000000149011612, and a f64 comparison would fail on the format.)

Those four are the only branches left, and each points at a different file. The
slot table exists twice (WGSL `const D_*` and JS `GpuSim.DIAG`), so
`tests/wgsl-struct.js` parses the generated prelude and pins every slot,
`layout.diagOut`, `reduceF`'s coverage of `RED_RELAX + plateCap`, and
`zeroFrame`'s branch shapes; `tests/gpu-play.js` writes known values into
`DIAG[14..16]` on the stub and asserts they arrive as the three state fields.
