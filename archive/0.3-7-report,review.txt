## Review of the last commit → root cause

The `loserRank` kernel in `js/gpu/wgsl-contact.js` (Phase VI, one workgroup per winner column) put three `workgroupBarrier()` calls inside control flow that the WGSL validator can't prove uniform:

- `aliveN()` is `u32(atomicLoad(&FOUT[FO_N]))` and the bin length comes from `scanOut()` — both **memory loads**. Dawn conservatively treats any memory-derived value as "possibly non-uniform," even though all 64 lanes provably read the same addresses.
- So `if (w >= aliveN()) { return; }`, `if (n <= 0) { return; }`, and the `nTiles` tile loops all make every barrier call non-uniform → parse failure → `GPU engine failed … back on CPU` at kernel build.
- The other barrier users (`scanA`/`scanB`) were never in trouble: their loop breaks on a power-of-two stride derived from a **constant**, so every lane does identical work.

A barrier path can only be driven by constants or workgroup builtins, and the tile count is data — so re-guarding can't fix it; the barriers had to go.

## The fix

`loserRank` is now **barrier-free**: each lane loads its target entry and ranks it against the whole bin with direct loads of the scratch block (same rank definition: count of smaller bin indices; same output: `LOSE[begin+rank)` ascending by column index, bin length unbounded). It's race-free because reads only touch the scratch block `[2COLCAP+begin, 2COLCAP+end)` while writes only touch the distinct slots of the first block (ranks are a permutation — each column is scattered exactly once), so no lane's read conflicts with any lane's write.

Cost: O(Lw²) loads per workgroup vs the tile sweep's O(Lw²)/64 workgroup-mem comparisons — for the typical single-digit Lw that's a handful of L2-cached loads *plus three barriers gone*; a mega-collision just lengthens the per-lane sweep (the heavy-overlap ≥5× acceptance is vs the pre-Phase-VI O(Lw·aliveN) baseline, which is still far worse).
